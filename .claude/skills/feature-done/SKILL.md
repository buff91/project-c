# 기능 마감

이 리포의 실제 실패 양상은 **기능은 되는데 마감이 밀리는 것**이었다 —
문서가 나중에 `docs:` 커밋으로 몰리고, 파일이 신(神) 클래스가 될 때까지 자라고,
테스트 수치가 낡는다. 아래를 순서대로 처리한다.

## 1. 테스트

`test` 스킬을 따른다. 최소한 Core shim은 돌린다. **초록이 아니면 여기서 멈춘다.**

새 로직에 EditMode 테스트를 추가했는지 확인한다. Core 규칙 테스트라면
UnityEngine 타입을 쓰지 않는다 — 그러면 shim에서도 자동으로 돌아간다.

## 2. 문서 — 기능과 **같은 커밋에**

무엇이 바뀌었는지에 따라 갱신 대상을 고른다. 해당 없으면 건너뛴다.

| 바뀐 것 | 갱신할 문서 |
|---|---|
| 게임 규칙(수치·판정·흐름) | `docs/SYSTEMS.md` — 규칙 SSOT |
| 마일스톤 진행 | `docs/ROADMAP.md` — 체크박스 + 근거 한 줄 |
| "지금 무엇이 돌아가나"가 달라짐 | `docs/STATUS.md` |
| 코드가 사는 계층/의존이 달라짐 | `docs/ARCHITECTURE.md` |
| 파일/파셜 배치가 달라짐 | `docs/CODE_STRUCTURE.md` |
| UI 배치·컴포넌트 | `docs/UI_ARCHITECTURE.md` / `docs/UI_DESIGN_SYSTEM.md` |
| 설계 방향 자체가 확정/변경됨 | `GDD.md` — 최종 SSOT |

**`CLAUDE.md`는 얇게 유지한다.** 자라나는 서술은 `docs/STATUS.md`로 보낸다.
CLAUDE.md는 규칙·진입점·불변 방침만 담는다.

## 3. 파일이 자라지 않았는지

건드린 파일이 **500줄을 넘겼으면** 관심사가 몇 개인지 세어 보고 사용자에게 보고한다.
이 리포는 `IsoPrototypeDemo`를 58KB까지 키운 뒤 6,700줄짜리 빅뱅 리팩토링을 했고,
그 뒤처리 커밋(`style: '}    }' 정리`)이 따로 필요했다. 작게 쪼개면 그게 없다.
**단, 분할 자체를 이 커밋에 섞지 않는다** — 별도 커밋/세션이다.

## 4. 범위 점검

이 변경이 **한 시스템**에 머물렀는지 확인한다. 무관한 시스템을 같이 건드렸으면
사용자에게 알리고 커밋을 쪼갤 것을 제안한다 — 나중에 되돌릴 수 없게 엉킨다.

구현 중에 **설계 결정**을 내렸다면(예: "장비도 익스트랙션 규칙을 타는가")
그 사실을 명시적으로 보고한다. `fix:` 커밋으로 위장시키지 않는다.

## 5. 커밋

- 커밋/푸시는 **사용자가 요청할 때만** 한다. 요청이 없으면 준비만 하고 보고한다.
- 메시지는 한국어(타입 접두사 `feat:`/`fix:`/`refactor:`/`docs:`는 영어 유지).
- 제목은 무엇이 달라졌는지, 본문은 **왜**와 판단 근거.
- 기능 + 테스트 + 문서를 한 커밋에 담는다.
