# 플레이테스트 리포트 → 조정안

`docs/ROADMAP.md`「콘텐츠 & 밸런스」의 미완 항목들은 코드가 아니라 **수치**를 기다린다.
게임은 이미 `RunTelemetry`로 다 기록하므로, 새로 계측을 붙이지 말고 저장된 리포트를 읽는다.

## 1단계 — 리포트를 확인한다

```bash
python3 Tools/Telemetry/analyze_run.py --aggregate
```

- 리포트는 판이 **끝나야**(승리·생환·사망·포기) 생긴다. 에디터 Stop으로 끊긴 판은 없다
  (디버그 창의 수동 `리포트 저장`은 예외).
- 저장 위치는 개발 프로필 아래 `development-profile/telemetry/run-*.json`이다.
- **리포트가 없으면 거기서 멈춘다.** 판을 한 번 돌려 달라고 요청하고, 과거 문서의 수치나
  일반적인 로그라이크 상식으로 조정안을 지어내지 않는다.

한 판만 자세히 볼 때는 `analyze_run.py`(인자 없이 = 가장 최근), 특정 파일은 경로를 넘긴다.

## 2단계 — 표본이 판단을 지탱하는지 본다

| 상태 | 할 수 있는 말 |
|---|---|
| `cheatsUsed` 판 | **표본에서 뺀다**(집계가 자동으로 제외하고 몇 건인지 알린다) |
| 깨끗한 판 1~2건 | **방향만** 말한다. "죽은 축인가 / 압도적인가"까지. 숫자를 바꾸지 않는다 |
| 3건 이상 | 수치 조정안을 낸다 |

표본이 얇은데 조정안을 요구받으면, 그렇게 말하고 **무엇을 더 보면 확정할 수 있는지**를
알려 준다(예: "아크 캐스터를 낀 판이 아직 없다").

## 3단계 — 축별 판정 규칙

### 원거리 (ROADMAP: 조정 축은 판당 사격 횟수 하나)

집계의 `실측 사격 간격`과 `재충전 상한 대비 %`를 함께 읽는다.

- **상한의 70% 이상** → 재충전이 병목이다. 사격이 자원 관리로 작동하고 있다.
  근접이 눈에 띄게 밀리면(사격 비중이 근접을 넘으면) 옛 무료 원거리로 회귀한 것 —
  `RechargeTurns`를 올린다.
- **30~70%** → 의도한 대역이다. 건드리지 않는다.
- **30% 미만** → **병목은 재충전이 아니다.** 재충전을 줄여도 사격 수는 안 늘어난다.
  사거리·피해·사선 중 무엇이 막는지를 먼저 본다(피해 1은 임시값이다). 이때
  `RechargeTurns`부터 만지면 축이 죽은 원인을 못 찾고 값만 흔든다.

### 해금 조건 (화상 12 · 처치 20 같은 임시값)

집계의 `판당 중앙값 / 임계값`을 본다.

- **매 판 달성** → 조건이 느슨하다. 해금이 선택이 아니라 통행세가 된다.
- **1.5~3판** → 의도한 대역(몇 판 안에 열린다).
- **0** → 그 축이 판에서 **아예 일어나지 않는다.** 임계값 문제가 아니라 그 행동이
  게임에 없거나 유인이 없는 것이다. 숫자를 내리지 말고 왜 안 일어나는지를 먼저 적는다.

### 지역별 의뢰

집계의 `항상 0` 목록이 곧 답이다 — 0인 지표로 의뢰를 만들면 아무도 달성하지 못한다.
0이 아닌 지표만 후보로 제안하고, 목표치는 판당 중앙값의 절반~1배 사이에서 고른다.

### 덤으로 항상 함께 보는 것

`무엇에 죽었나`(치명타 원인)와 구간 곡선. 특정 적·원인에 치명타가 몰리면 밸런스가 아니라
그 적의 설계 문제일 수 있다 — 수치 조정안과 섞지 말고 따로 적는다.

## 4단계 — 조정안 형식

각 항목을 **"어디의 무엇을, 얼마로, 왜"** 세 줄로 낸다. 값의 SSOT는 코드다:

| 조정 대상 | 값이 사는 곳 |
|---|---|
| 원거리 기본 티어 | `Core/RangedWeaponRules.cs` → `Baseline.Range/Capacity/RechargeTurns` |
| 아크 캐스터 | `Core/Equipment.cs` → `arc-caster`의 `rangedRange/rangedCapacity/rangedRechargeTurns` |
| 해금 조건값 | `Core/ItemUnlockRules.cs` → `Conditions` |
| 의뢰 목표치 | `Core/BountyRules.cs` → 의뢰 정의의 `target` |

**임계값을 문서나 도구에 베끼지 않는다.** `analyze_run.py`는 위 파일들에서 값을 읽으므로,
코드를 고치면 다음 리포트가 자동으로 새 기준으로 나온다.

## 5단계 — 조정을 실제로 넣을 때

1. **수치만 바꾼다.** 규칙(판정 구조)을 함께 바꾸면 다음 리포트가 무엇 때문에 달라졌는지
   알 수 없다. 규칙 변경이 필요하다고 판단되면 그건 별도 설계 결정으로 올린다.
2. 관련 테스트가 값을 하드코딩하고 있으면 함께 고친다(`./Tools/CoreTests/run-core-tests.sh`).
3. `docs/SYSTEMS.md`의 해당 수치와 `docs/ROADMAP.md`의 해당 미완 항목을 **같은 커밋에서**
   갱신한다. "실플레이 전 임시값" 표기를 지우거나, 무엇을 근거로 정했는지 남긴다.
4. 조정 근거가 된 리포트의 판 수와 중앙값을 커밋 메시지에 적는다 — 다음 조정이
   같은 표본을 다시 읽지 않아도 되게.

## 보고 형식

```
표본: 깨끗한 판 4건 (치트 1건 제외) · 중앙 480턴

원거리   사격 18발 · 26.7턴/발 · 재충전 상한의 22%
         → 재충전은 병목이 아니다. 값을 만지기 전에 사거리 3과 피해 1을 본다.

해금     FrostBomb 7/12 (1.7판) — 대역 안, 유지
         OilFlask  0/3        — 폭발통을 아무도 안 민다. 임계값이 아니라 유인 문제.

의뢰     WaterFrozen·BarrelPushes 가 항상 0 — 이 둘로는 의뢰를 만들지 않는다.
```

숫자를 내지 못하는 항목은 **"표본 부족"이라고 쓴다.** 비워 두거나 그럴듯한 값으로 채우지 않는다.
