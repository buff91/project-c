# 시스템 설계 요약 (에이전트용)

> `GDD.md` §5의 상세를 코딩 판단용으로 압축. 충돌·모호 시 **GDD가 최종 출처**.

## 플레이테스트 텔레메트리

- `RunTelemetry`는 Core의 직렬화 가능한 집계 모델이다. Unity 시간·파일 API를 모르며
  Gameplay가 실제 이벤트와 unscaled delta time을 전달한다.
- 층별 시간/턴/피해/처치/획득, 피해 원인, 아이템 획득·사용·조합, 플레이어/적 낙하,
  화상·빙결 부여와 기름 발화·물 결빙/증발을 기록한다.
- `RunSaveData.telemetry`로 층 체크포인트와 함께 이어지며, 승리/생환/사망/포기에서
  `development-profile/telemetry` 아래 JSON으로 자동 확정된다.
- 디버그 창은 실시간 압축 요약과 수동 `리포트 저장`을 제공한다. 게임플레이 치트를
  사용한 런은 `cheatsUsed`로 표시해 정상 밸런스 표본과 섞이지 않게 한다.
- 휴식처 사용 횟수와 총 회복량, 숨은 방 발견 횟수도 기록한다. 텔레메트리 스키마 v3부터
  `restSitesUsed`/`healingFromRest`/`secretRoomsFound`를 사용한다.
- **깊이 구간 롤업(v4)**: 층별 기록에 아이템 사용/조합·휴식·숨은 방이 추가되고,
  `RefreshBands()`가 이를 `DungeonDepthBandRules` 경계로 다시 묶어 `bands`(초반 1~3번째 /
  중반 4~6번째 / 후반 7~9번째 / 보스 10번째+)를 만든다. **파생 값이라 따로 기록하지 않는다** —
  저장·요약 직전에 재계산하므로 경계를 바꾸면 과거 리포트도 같은 규칙으로 다시 묶인다.
  구간별 체류(시간/턴)·피해·처치·아이템을 JSON 리포트와 디버그 창에서 나란히 비교한다.
  사람이 읽는 구간 라벨의 SSOT는 `DungeonDepthBandRules.RangeLabel`/`BandLabel`이다 —
  예전에는 `B1~B3`처럼 지하 층 표기를 박아 뒀는데, 상승·`Inward` 던전에서 화면에 거짓이 된다.
- **진행 지수 축(v5)**: `currentProgressIndex`/`deepestProgressIndex`가 `currentFloorIndex`/
  `deepestFloorIndex`와 **별도로** 실린다. 상승·`Inward` 던전에서는 층 인덱스로
  "얼마나 나아갔나"가 성립하지 않기 때문이며(의뢰의 `DeepestDepth`가 음수로 굳던 버그가 여기서 왔다),
  구간 롤업도 이 값을 키로 쓴다.

## 중간 생환 (익스트랙션 지점)

- `ExtractionRules`가 SSOT. **비상 탈출구는 4번째·8번째 층 두 곳뿐**이다
  (`ExtractionDepths = { 3, 7 }` — 진행 지수다. 층 라벨로 쓰지 않는다: 폐병원은 상승이라
  4번째 층이 `B4`가 아니라 `2F`이고, 침수된 금고에서는 `4구역`이다). 사이 구간
  (1~3 / 5~7 / 9~10번째)이 곧 물러설 수 없는 구간이며, **최심층 출구는 보스를 잡아야 열린다**
  (보스가 없는 원정지는 상시 개방 — 아래 "원정지 진행 / 보스 출구" 참조). 자리는 입구에서
  가장 먼 남쪽 방으로 결정론적으로 고른다 — 층에 들어서자마자 나가는 게 아니라 돌아 나오는
  동선이 되게.
- 탈출구를 밟으면 출구와 같은 선택 모달을 띄우되 문구가 다르다: **"계속 탐색" vs "생환"**.
  생환은 출구와 같은 `ExtractRun` 경로라 정산 규칙이 하나로 유지된다.
- **비상 송출기**(`ItemKind.ExtractionBeacon`): 어디서든 즉시 생환. 상점 고가($70)이며
  숨은 방 보상에서 **아주 가끔만**(`BeaconRewardChancePercent`) 나온다 — 흔하면
  "살아 나갈 권리"가 아니라 기본 소지품이 되고 탈출구가 무의미해진다.
- 배고픔과 짝을 이룬다: **다음 탈출구까지 버틸 식량이 있나**가 곧 "더 내려갈까"의 답이다.

## 배고픔 (부드러운 시계)

- `HungerRules`/`HungerState`가 SSOT. 포만도는 턴마다 1씩 줄고, `HungryThreshold` 아래면
  경고, 0이면 `StarvingDamageInterval`턴마다 HP 1을 깎는다. **즉사시키지 않는다** — 신호만 준다.
- **하드 타이머를 쓰지 않는 이유**: 파밍이 기둥 4라 제한 턴은 탐색·조합·숨은 방을 통째로 죽인다.
  배고픔은 자원으로 관리되는 압박이라 탐색은 살리고 무한 캠핑·무의미한 왕복만 막는다.
- **단계는 SPD와 같다**: 포만 → 배고픔(경고만, 나중에 별도 상태이상을 붙일 자리) →
  굶주림(주기적 HP 감소). 배고픔 단계는 HP를 건드리지 않는다.
- 통조림(`ItemKind.CannedFood`)이 답이다. 던전 스폰 테이블(5/23)과 상점에 있고, 먹는 데 행동
  1회를 쓴다. 가득 찬 배 100턴 / 한 통 60 — 한 층 정리를 40~60턴으로 잡으면
  **가득 찬 배가 두 층을 채 못 버티는 주기**라 판마다 한두 번이 아니라 중간중간 자주 먹는
  리듬이다(임시값, 실플레이로 재조정). 한 통이 배를 다 채우지 않는 것도 같은 이유다.
- 배고픔은 **판 전체를 관통한다**. 층·던전 체인이 바뀌어도 이어지고 체크포인트에 저장되며,
  모닥불 휴식은 HP만 회복할 뿐 배를 채우지 않는다.
- 텔레메트리에 굶주린 턴 수(`starvingTurns`)와 굶어서 잃은 HP(`starvationDamage`)를 기록해,
  압박이 실제로 물렸는지 리포트로 본다.

## 장비 (플레이어 전투 방식)

- **원칙: 장비는 숫자가 아니라 행동 규칙을 바꾼다.** 어떤 장비에도 공격력 보정이 없다 —
  GDD §11이 경계한 것은 영구 스탯 강화이고, 권한 것은 장비/시작 장비 해금이다.
  옛 대장간 영구 티어 강화(무기 연마·방어구 보강·도구 정비)는 **제거**했다.
- 슬롯은 무기 1 + 보조 1. `EquipmentCatalog`가 단일 출처다. 제작·장착 창구인 **대장간은
  6번째 층(진행 지수 5)의 대장장이를 구출해야 열린다**(`ShelterNpcRoster` — 아래 "동료 구출 ·
  쉘터 시설"). 장비 4종이 통째로 그 시설에 종속된다.
  - 긴 파이프: 근접 사거리 2(직선, 사이가 뚫려 있어야 함). 이미 닿으면 걸어 붙지 않고 그 자리에서 찌른다.
  - 대형 렌치: 근접 명중 시 1칸 넉백 — 구멍·창문·허공 앞에서는 그대로 낙하로 이어진다(`KnockbackRules`).
  - 표지판 방패: 받는 물리 피해 -1(최소 1은 남는다). 백팩 2×2를 차지한다. 상태이상 틱에는 적용하지 않는다.
  - 완충 부츠: 안전 낙하 높이 +2 — 뛰어내리기가 이동 수단이 된다
    (`FallRules.DefaultSafeFallHeight`(0) + `EquipmentDefinition.SafeFallBonus`(+2)를
    `EquipmentRules.LoadoutFor`가 합쳐 `CombatLoadout.SafeFallHeight`로 넘긴다).
- 장비는 `ItemKind`라 창고·세이브를 공유하지만, **장착 장비는 백팩 공간을 쓰지 않고**
  출정 준비 격자에도 나오지 않는다(대장간에서 관리).
- **장비도 익스트랙션 규칙을 탄다(다크앤다커 모델).** 장착한 장비는 출발 시 창고에서 빠져나가
  원정에 반입되고, **죽거나 포기하면 소모품과 함께 잃는다**. 살아 나오면(생환·승리) 창고로
  돌아오며 장착 상태도 유지된다. 던전 체인 전환에서는 이미 들고 있는 장비를 그대로 이어 가고,
  이어하기는 체크포인트의 반입 기록(`RunSaveData.carriedWeaponId/GearId`)에서 복원한다.
  **창고에 남긴 예비 장비는 안전하다** — 무엇을 걸고 나갈지가 곧 판돈이다.
- **던전에서도 장비가 나온다**(`EquipmentDropRules`): 4번째 층(진행 지수 3)부터 층당 최대 하나,
  30% 확률. 주우면 백팩 면적을 먹고(긴 파이프·대형 렌치 1×2 · 표지판 방패 2×2 · 완충 부츠 1×1),
  해당 슬롯이 비어 있으면 즉시 장착한다
  (이미 낀 장비를 말없이 갈아치우지 않는다 — 슬롯이 차 있으면 백팩에 남는다).
  장착한 순간부터 반입 장비와 같은 운명이라 죽으면 잃고, 살아 나와야 창고로 들어간다.
  - **단, 대장장이를 구출하기 전에는 아예 나오지 않는다**(`Roll(..., forgeOpen)` ←
    `meta.IsFacilityOpen(ShelterFacility.Forge)`) — 쓸 수도 고칠 수도 없는 장비를 줍게 하지 않는다.
    **롤은 그대로 소비하고 결과만 막는다**: 대장간 상태가 던전 나머지의 seed 재현을 흔들면
    같은 seed가 같은 던전이라는 전제가 깨진다.
- 전투 보정은 `CombatLoadout` 하나로 모아 `CombatRules`가 파라미터로 받는다 —
  나중에 몬스터가 장비를 들어도 같은 경로를 쓴다.
- **골드의 목적지가 장비다.** 영웅 해금($200)이 사라지면서 생환 보상이 갈 곳이 소모품밖에 없어
  골드가 남아돌았고, 그러면 "무엇을 걸고 나갈지"가 판돈이 아니게 된다. 4종 제작비를 그만큼 올렸다:
  55/65/50/45 → **105/125/95/85**(합계 $215 → $410). 임시값 — 생환 밸런스 재조정 때 함께 본다.
- 골드 표기의 SSOT는 `ItemCatalog.FormatGold`다 — 픽셀 HUD에서 즉시 읽히도록 `G`가 아니라
  **`$` 접두사**를 쓰고 HUD·상점·정산 화면이 같은 형식을 공유한다.

## 원정자 (직업 없음)

- `SurvivorProfile` 상수 하나가 플레이어 기본 수치의 SSOT다: HP 10 · 근접 3 · 원거리 1 · 물약 1.
  **프리셋도 직업도 없다 — 모든 원정자는 같다.**
- **왜 영웅을 걷어냈나.** 익스트랙션 모델이고 스킬 트리가 없다. 정체성은 이미 **장비**가 지고
  있으며(장비는 설계상 숫자가 아니라 규칙을 바꾼다), 옛 영웅 3종은 HP/공격력 **숫자만** 달라
  고르는 행위가 전술이 아니라 난이도 선택이었다. 무엇을 걸고 나갈지가 판돈인 게임에서
  캐릭터를 먼저 고르게 할 이유가 없다.
- 값은 **옛 기사 그대로**다 — 기사는 해금이 필요 없는 기본 영웅이었으므로 기본 경로를 밟던
  플레이어의 밸런스가 바뀌지 않는다.
- 세이브·텔레메트리의 `heroId`/`unlockedHeroes`는 제거했다. **옛 세이브는 해당 필드를 무시하고
  로드되므로 마이그레이션이 없다.**
- 비주얼은 `IsoVisualCatalog.SurvivorSprite`이며 knight 슬롯을 그대로 쓴다(씬 인스펙터 연결 유지).
  ranger/alchemist 슬롯은 **지역별 원정자 스킨** 자리로 남겼다.

## 해금 · 기록 (재도전 동력)

- **해금 판정은 「이번 판」이 아니라 「역대 최고 + 투입 기록」이다**(`ItemUnlockRules`).
  조건이 한 판 기준이면 화상을 11번 입히고 죽은 판이 통째로 버려져 "실패한 판도 전진"이
  문서에만 있게 된다. 한 판에 몰아치는 도전은 그대로 **빠른 길**로 남는다 —
  최고 기록은 여전히 한 판의 값이다.
- **기록(`RunRecordRules`)은 죽음이 먹이는 축이다.** 판이 끝날 때마다 적립되고 기록실에서
  조건에 투입한다(1 기록 = 조건 진행 1).

      기록 = 반복한 층 × 1 + 개척한 층 × 3 + 숨은 방 × 2
      (개척한 층 = max(0, 도달 층 − 역대 최고) · 반복한 층 = 도달 층 − 개척한 층)

  - **개척은 역대 최고를 넘은 층만** 센다. 도달 층에만 비례하면 1~3층 왕복이 최적 파밍이 된다.
    그래도 반복이 0은 아니다 — 0이면 원래 문제로 돌아간다.
  - 그래서 **×1은 도달 층 전체가 아니라 이미 가 본 층에만** 붙는다. 두 요율을 같은 층에
    겹쳐 세지 않는다 — 도달 5·역대 최고 2면 2×1 + 3×3 = 11이지 14가 아니다.
    수치의 SSOT는 `RunRecordRules.RepeatRatePerFloor`/`FrontierRatePerFloor`/`SecretRoomRate`.
  - **적립은 정산과 무관하다.** 죽음만 보상하면 자살이 전략이 되고, 생환만 보상하면
    고치려던 문제가 그대로다.
  - **적립이 기준선 갱신보다 먼저**다(순서가 뒤집히면 첫 판이 가장 손해본다 — 테스트로 고정).
- **왜 물자가 아니라 기록인가.** 죽으면 소지품 전손이 익스트랙션의 긴장이고 GDD §11은 영구 스탯
  강화를 금지한다. 둘 다 안 건드리려면 죽음이 남기는 것은 물자도 능력치도 아니어야 한다 —
  돌아오지 못한 원정자가 쉘터에 남기는 건 정보이고, **늘어나는 것은 숫자가 아니라 선택지**다.
- 투입은 **부족분과 보유량 중 작은 쪽**을 한 번에 넣는다(1개씩이면 목표 20에서 스무 번을 누르고,
  부족분보다 많이 받으면 기록을 버린다). 모자라도 실패시키지 않는다 — 넣은 만큼 진행이 남는 것이
  이 축의 요점이다.
- **판정은 Core 한 곳뿐이다**(`ItemUnlockRules.InvestRecords`/`RemainingFor`). UI가 자체 판정을 들면
  "기록실에선 열리는데 판 끝나면 안 열린다"가 생긴다 — 두 경로가 같은 `RunRecordRules.IsConditionMet`을
  쓴다는 것을 테스트로 고정했다.
- **"다음에 열릴 것" 안내도 같은 자로 잰다.** `ItemUnlockRules.ClosestPending(meta)`는 거리를
  `RemainingFor`(역대 최고 + 투입 기록) 하나로만 재고 이번 판 계측을 보지 않는다. 예전에는 이
  함수만 이번 판 값을 읽어서, 기록실과 판 종료 화면이 같은 조건을 다른 숫자로 말했고 투입한
  기록이 안내에 아예 안 잡혔다. 안내를 의뢰에 맡길 수도 없다 — **의뢰 게시판 자체가 잠기는
  시설**이라 순환이 된다. 그래서 잠기지 않는 두 경로(판 종료 화면·기록실)가 안내를 맡는다.
- 판 종료 화면이 "기록 +N"을 알린다. 이 줄이 없으면 플레이어는 죽음을 "아무것도 못 건졌다"로 읽고,
  그게 곧 재도전하지 않는 이유가 된다.
- 수치(1/3/2, 1 기록 = 진행 1)는 실플레이 전 임시값이다.

## 동료 구출 · 쉘터 시설

- `ShelterNpcRoster`가 SSOT. 던전에 갇힌 동료를 구출하면 쉘터에 **시설**이 생긴다 —
  재도전 동력의 두 번째 갈래(첫째는 도구 해금)이며, 거점이 자라는 감각을 담당한다.
  현재 둘: **연락책 → 의뢰 게시판**(진행 지수 2 = 3번째 층) · **대장장이 → 대장간**(진행 지수 5 = 6번째 층).
- **층은 고정이고 등장은 확률이 아니라 보장이다.** 확률로 두면 운이 나쁜 플레이어의 시설이
  영원히 안 열리고 되돌릴 방법이 없다. 그래서 미구출 NPC가 있으면 그 층에 **반드시**
  갇힌 방(막다른 분기 방)이 생기고, 생성기가 북쪽 방을 오른쪽으로 밀어서라도 자리를 만든다.
- **초반 → 중반 배치**인 이유: 둘 다 깊으면 첫 판에 아무도 못 만나 초반 허브가 너무 오래 빈다.
- **숨은 방과 겹치지 않는다.** 숨은 방은 벽으로 위장해 못 찾을 수 있어서 거기에 NPC를 두면
  시설 해금이 영구히 막힌다. 생성기가 NPC 층을 먼저 정하고 숨은 방 후보에서 뺀다
  (아래 "숨은 방" 참조).
- **상인·창고·기록실은 잠그지 않는다.** 파밍 → 골드 → 상점 루프가 첫 판부터 돌아야 하고,
  기록실은 "무엇을 해야 하는지" 배우는 창구라 항상 열려 있어야 한다.
- 자리는 분기 방의 문에서 가장 먼 안쪽 모서리다 — "갇혀 있다"가 그림으로 읽힌다. RNG를 쓰지 않는다.
- **구출하면 즉시 저장한다.** 그 판에 죽어도 합류는 남는다 — 구출은 소지품이 아니라 진행이고,
  "실패한 판도 전진"이 여기서도 성립해야 한다. 같은 사람을 두 번 구출하는 방은 만들지 않는다.
- 한 판에 미구출 동료가 **여럿이면 전부** 각자의 층에 갇힌 방을 얻는다(첫 판이면 둘 다).

## 의뢰 (현상금)

- `BountyRules`가 SSOT. 허브 게시판에서 계약을 받고 **살아 나올 때만**(생환·승리) 정산한다 —
  계약의 조건은 무사 귀환이다. 정산 후 활성 목록은 완료·미완료 모두 비운다(허브에서 다시 받는다).
- **계측을 새로 만들지 않는다.** 완료 판정의 백엔드는 `RunTelemetry` 누적값이고,
  `BountyMetric` 11축(처치·보스 처치·최심 진행·적 낙사·의도적 낙하·화상/빙결 부여·기름 발화·
  물 결빙·숨은 방·폭발통 밀기)이 각각 텔레메트리 필드 하나에 대응한다. 해금 조건
  (`ItemUnlockRules`)도 **같은 축을 재사용**한다.
- **최심 진행은 진행 지수를 그대로 읽는다**(`deepestProgressIndex`). 예전에는
  `-deepestFloorIndex`로 역산했는데, 상승 던전에서는 층 인덱스가 양수라 값이 음수가 되어
  그 의뢰가 영원히 미완이었다.
- 제시는 seed로 중복 없이 3건(`OfferCount`) — 같은 seed면 같은 의뢰다.
- 목표 수치·보상 골드는 밸런스 전 자리표시값이다.

## 콘텐츠 변주 — (지역 × 깊이)

- `DungeonBandProfile` 하나가 구간 정체성의 SSOT다: 적 조합 가중치·추가 적 수·분기/웅덩이 확률 +
  캐치워크 길이(`CatwalkLength`) + 벽 등잔 희소도(`WallSconceRarity`). 경계는 `DungeonDepthBandRules`.
  여기에 **일반 아이템 드롭 편성**(`DungeonLootRules`)이 지역 축으로 하나 더 붙는다.
- **표는 두 축이다**: `DungeonBandProfiles.ForDepth(region, depthIndex)`. 깊이가 기울기를 주고
  **지역(`DungeonRegionProfile`)이 그 기울기의 기준선**을 옮긴다. 지역은 던전 ID가 아니라
  **공유 가능한 프로파일**이라 원정지가 늘어도 표가 던전 수만큼 커지지 않는다.
  던전 → 지역 매핑은 `DungeonDefinition.Region`이 소유하고 `DungeonLayout.Region`으로 실려간다
  (`Direction`과 같은 이유 — 전역에서 읽으면 던전 체인의 2번째 던전이 1번째 값을 쓴다).
- **지역이 가르는 것은 적 혼합·밀도·무대 확률·드롭 편성이다.** 아키타입의 HP·공격력·행동 트리는
  전 지역 공용이다(`MonsterRoster`) — 리스킨 원칙대로 **시스템은 하나, 얼굴만 지역별**.
- **드롭 편성도 지역이 가른다**(`DungeonLootRules.Resolve(region, progressIndex, roll)`).
  침수된 금고는 기름 병을 빼고 그 자리를 냉기 폭탄에 넘긴다(냉기 1 → 3) — 물 위에서 기름은
  지역 반응(빙결·감전)을 흐린다. **롤 수는 지역과 무관하게 23 고정**(`RollCount`)이라
  지역을 바꿔도 생성기 RNG 스트림이 밀리지 않는다.
- **지역은 인자로 강제한다**(기본값 없는 필수 매개변수). 축이 하나 더 생겼는데 호출부가
  생략할 수 있으면 옛 `DungeonDepthBandRules.ForFloor`처럼 조용한 오답이 다시 생긴다.
- 현재 세 지역: `Facility`(폐병원 — 기준선) · `Flooded`(침수된 금고 — 웅덩이↑·광원↓·사수↓) ·
  `Ember`(잿불 성채 — 웅덩이↓·밀도↑·광원↑). **깊이의 방향은 지역과 무관하게 유지한다** —
  잿불 성채가 전반적으로 밝아도 그 안에서 깊어질수록 어두워진다(테스트로 고정).
- **기름 무대는 아직 지역 축에 없다** — 기름은 아이템(`OilFlask`)일 뿐 생성기가 타일에
  깔지 않는다. 잿불 성채를 열 때 `PlacePuddle`에 대응하는 배치를 새로 만들어야 한다.
- **구조**: 사다리 위 +2단 캐치워크를 밴드 길이만큼 얹는다(Shallow 0 / Mid 1 / Deep·Boss 2).
  최심층 아레나는 결투 공간을 비운다. 결정론적 배치라 생성 RNG 스트림을 흔들지 않고,
  사다리 링크로만 올라가므로 도달성 불변식이 유지된다. +2단은 높이 인식 FOV 차폐·내려치기·
  고지대 사격이 실제로 발동하는 층 내부 무대다.
- **광원/소품**: 등잔 희소도가 깊어질수록 커진다. 광원 필드(`IsWallSconceTile`)와 벽 소품
  (`CreateRearWall`의 횃불)이 같은 값을 공유해 빛과 장식이 같은 방향으로 읽힌다.
- **팔레트는 깊이로 바뀌지 않는다(확정 규칙)**: `IsoVisualCatalog.DungeonSurfaceFor`는 모든 깊이에서
  같은 공통 석재색을 낸다(테스트로 고정). 시각 변주는 밴드 스프라이트 슬롯과 위의 구조·광원으로만 준다.

## 숨은 방

- `SecretRoomRules`가 첫 던전 길이에 따른 개수(10층=3), 인접 조사, 폭발 공개 규칙의 SSOT다.
- 생성기는 **마지막(보스) 층을 뺀 1~9번째 층** 중 seed로 고른 세 층의 막다른 분기를 비밀 분기로
  강제한다. 메인 진행 경로에는 넣지 않으며, 같은 seed는 비밀 층·입구·보상 위치까지 재현한다.
- **미구출 동료가 갇힌 층도 후보에서 뺀다**(`ShelterNpcRoster.PendingFloors` → `PickSecretDepths`).
  숨은 방은 못 찾을 수 있어서 거기에 NPC를 두면 시설 해금이 영구히 막힌다. 미구출 NPC가 없으면
  제외 집합이 비어 후보와 RNG 소비가 예전 그대로다(같은 seed = 같은 던전). 후보가 모자라면
  그만큼 개수가 줄어든다.
- `DungeonFloorInfo.SecretDoor/SecretRoomTiles/SecretReward`가 생성 결과를 명시한다.
  공개 전 `SecretDoor`는 단단하지만 걷지 못하고 시야를 막는다. 공개 시 다시 닫을 수 없는
  `SecretPassage`로 바뀐다.
- 비밀문은 멀리서 일반 석벽처럼 보이고 4방향 인접 시 균열이 금색으로 약하게 빛난다.
  HUD/Space 상호작용은 `수상한 벽 조사`를 우선 제시한다. 폭탄·냉기 폭탄의 3×3 범위도 공개한다.
- 방 내부 보상은 초반 층 `Gemstone`, 4번째 층(진행 지수 3)부터 `Relic`을 한 개 보장한다. 공개 전에는 FOV 차단으로
  월드 아이템과 미니맵 구조가 보이지 않고, 공개 후 일반 아이템 획득 규칙을 그대로 사용한다.

## 제한 휴식처

- `DungeonRestRules`가 등장 깊이와 회복량의 SSOT다. 첫 층·보스 층을 제외하고 세 층마다
  (`DepthInterval = 3`) 두므로 10층 던전에서는 **4번째·7번째 층**이며, 잃은 HP의 절반을 올림해 회복한다.
- `DungeonFloorInfo.RestSite`는 지형을 바꾸지 않는 관심 지점이다. 생성기는 일반 Floor 위에
  프롭을 두고 적·아이템·물 웅덩이와 겹치지 않게 한다.
- 휴식은 상태이상을 제거하지 않고 1행동을 소비한다. 런 전체에서 장소당 한 번만 쓸 수 있으며,
  사용한 전역 층 인덱스는 `RunSaveData.usedRestFloorIndices`로 체크포인트와 던전 전환에 이월한다.
- Gameplay는 FOV 밖 휴식처를 숨기고, 사용 후 모닥불을 어둡고 작게 표시한다.

## 위험 프롭 초기 배치

- `DungeonPropPlacementRules`가 폭발통 같은 상호작용 프롭의 안전 좌표를 고른다.
- 시작/층 입구에서 맨해튼 거리 2칸 이상인 일반 `Floor`만 허용하고, 적·아이템·계단·휴식처·
  구출 대상·생환 지점·보스 랜드마크와 겹치지 않아야 한다.
- 90도 시점 회전 어느 방향에서도 입구와 같은 화면 세로축에 투영되는 대각선 좌표는 제외한다.
  격자상 다른 칸이어도 캐릭터 뒤에 포개져 같은 위치처럼 보이는 배치를 막기 위해서다.
- 안전 후보가 없으면 입구를 fallback으로 쓰지 않고 해당 프롭을 생성하지 않는다.

## 백팩 / 창고 — §5.6

- 던전 백팩은 `BackpackRules`의 6×4 격자다. `ItemKind → ItemFootprint` 매핑과
  큰 아이템 우선 자동 배치를 Core에서 계산하고 UI는 `BackpackLayout`을 그대로 그린다.
- 1×1 소형, 1×2 기름 병/투척 단검/귀환 두루마리, 2×2 유물로 시작한다. 장비도 같은 표에 있다 —
  긴 파이프·대형 렌치 1×2, 표지판 방패 2×2, 완충 부츠 1×1. 회전은 없다.
  면적의 SSOT는 `ItemCatalog`(`OneCell`/`Tall`/`Large`) 하나다 — 장비 절과 여기가 갈라지면
  "주웠는데 안 들어간다"가 규칙이 아니라 버그로 읽힌다.
- 백팩 공간 부족 시 획득은 실패하고 월드 아이템은 활성 상태로 남는다.
- **점유율 게이지**(`BackpackPressure`): 인벤토리 모달의 소지품 칸 위에 `UsedCells / Capacity`를
  막대로 그린다. `WarningRatio`(0.8) 이상이면 `--pc-hazard`로 바뀐다 — "이제 곧 못 줍는다"는
  경고다. 숫자("22 / 24 칸")는 예전부터 있었지만 압박이 한눈에 안 읽혔다. **비율과 경고 판정은
  Core가 소유한다** — UI가 자체 판정하면 숫자와 막대가 다른 말을 하는 상태가 조용히 생긴다.

- **충전(회분)**: `ItemDefinition.ChargesPerItem`이 "백팩 한 칸이 담는 사용 횟수"를 정한다.
  이 값이 1보다 크면 `ItemKind → int`가 세는 것은 개수가 아니라 **총 사용 횟수**이고,
  점유 칸수는 `ChargeUnits.UnitsFor` = `ceil(충전 / 칸당)`으로 **파생**한다.
  마지막 칸만 덜 찰 수 있고 나머지는 만충이다(`ChargesInUnit`).
  칸수 파생을 `ItemCatalog`가 아니라 `BackpackRules`에 둔 이유는 그게 경제가 아니라
  패킹 규칙이기 때문이다. 잔여 충전은 `BackpackPlacement.Charges`로 UI에 실려 나간다 —
  UI가 다시 계산하면 숫자와 그림이 다른 말을 하는 상태가 조용히 생긴다.

> **충전 > 1은 소모품에만 허용한다 — 이 불변식이 설계의 안전 예산 전체다.**
> 전리품 정산(`GoldValue × count`)·조합 재료 판정(`>= 2`)·장비 보유 판정(`GetCount > 0`)에는
> "count가 곧 개수"라는 가정이 그대로 남아 있다. `ItemDefinition` 생성자가 정적으로 거부하고
> (`ItemCatalog` static 초기화 시점에 터진다) 테스트가 전 종류를 순회해 못박는다.
> 탈출 자원(송출기·귀환)도 영구히 1이다 — 2충전 송출기는 공짜 탈출 2회라 익스트랙션 판돈이
> 무너진다.

> **장비 내구도는 여전히 없다.** 충전은 "한 칸에 몇 회분"이지 "장비가 닳는다"가 아니다.
> 내구도를 도입하려면 마모율·파손 처리·수리(대장간 경제)·세이브 포맷이 함께 정해져야 하고,
> 그건 여기(SYSTEMS)와 GDD가 먼저 결정할 일이다.
- 허브 창고는 48칸 표현을 쓰되 종류별 중첩 저장이며, 던전 백팩의 개별 면적 규칙과 구분한다.
- `ExpeditionLoadoutRules`가 창고 ↔ 출정 백팩의 한 개 단위 이동, 기본 지급품 포함 배치,
  공간 부족 거부와 초과분 창고 복귀를 담당한다. **기본 지급품은 이제 하나다** — 영웅이 없어져
  `CreateInventory`가 hero 인자를 받지 않고 `SurvivorProfile.StarterCount`를 읽는다.
- `MetaSaveData`는 창고 수량과 출정 선택 수량을 별도로 저장한다. 허브 UI는 모바일 선택+반대편 탭과
  PC 드래그/버튼을 같은 전송 규칙으로 호출하고, 실패한 이동은 데이터 변경 없이 빨간 드롭 피드백을 낸다.
- 던전 진입 시 `ConsumeLoadout()`이 선택 물품만 런 인벤토리로 이동한다. 선택하지 않은 창고 물품은
  유지하며, 예외적인 배치 초과분도 삭제하지 않고 창고로 되돌린다.

## 다층 격자 (Foundation) — §5.1

- 논리 좌표 `GridPos { int x, y, int elevation }`.
  - `elevation` = **연속 높이값** (단순 층 번호 아님). 한 층 안에서도 높이차 존재 (계단/경사, BG3식 멀티 높이).
- "층(floor)" = elevation을 크게 묶은 논리 구획.
- 용어 경계:
  - **진행 지수(`DepthIndex` → `ProgressIndex`)** = 몇 번째로 방문하는 층인가. 휴식처, 탈출구,
    장비 드랍, 숨은 방, 적 조합, 구간 변주, 보스가 전부 이 값을 키로 쓴다.
    **elevation에서 파생하지 않는다** — 생성기가 경로를 깔면서 층에 부여한다(GDD §5.1).
    던전은 상승·하강·평면이 모두 가능하고 한 던전 안에서 방향이 섞일 수 있으므로,
    고도로 역산하는 순간 비단조 경로에서 성립하지 않는다.
  - `FloorIndex` = elevation을 던전 층으로 묶은 **공간** 구획. 진행 순서와 무관하다.
  - **진행 방향(`DungeonProgressDirection`)** = 던전별 데이터다. **전역 스위치가 아니다.**
    `DungeonDirectionRules`가 SSOT이며 세 가지가 공존한다:
    - `Descend` — 아래로 파고든다(지하 시설·지하묘지).
    - `Ascend` — 위로 올라간다(폐병원·탑).
    - `Inward` — **고도가 축이 아니다.** "얼마나 깊이 들어왔는가"가 진행이고 오르내림은
      층 안의 국소 지형일 뿐이다(침수 도관·잠식 구역). 층은 여전히 쌓이지만 그건
      렌더·컬링을 위한 **엔진 사정**이지 플레이어가 보는 사실이 아니다 —
      라벨도 `B1`/`1F` 가 아니라 `1구역`이고, 층 전환은 계단이 아니라 통로로 읽힌다.
    - **공간(위/아래) ≠ 진행(진출/귀환).** `StairsUp/Down`은 공간 이름이라 고정이고,
      "다음 층으로 가는 계단"이 둘 중 무엇인지만 방향을 탄다 —
      하강은 진출=`StairsDown`, 상승은 진출=`StairsUp`(`OnwardStair`/`BackStair`).
      `FinalFloorIndex`를 `BottomFloorIndex`에서 갈라낸 것과 같은 구분이다.
    - **중력은 방향을 타지 않는다.** 낙하·수직 시야는 언제나 아래로 향하므로 `FallRules`·
      `SightRules`는 방향을 모른다. 바뀌는 것은 규칙이 아니라 의미다 — 하강에서 낙하는 전진
      지름길, 상승에서는 후퇴·탈출 수단(`FallAdvancesProgress`).
    - 표시 층 번호는 **건물에 0층이 없다**는 걸 반영한다(`B2 → B1 → 1F`). 던전은 시작 건물 층
      (`FirstBuildingFloor`)만 선언하고 라벨은 `FloorLabelFor`가 만든다.
  - `Elevation` = 정렬·낙하·공간 연결에 쓰는 연속 높이 좌표.
  - `LocalHeight` = 같은 던전 층 안의 단차. 돌출 바닥·계단 비주얼이 사용한다.
  - `TileKind.Floor` = 걸을 수 있는 바닥 타일 타입이며 던전 층(floor)과 다른 개념이다.
- `DungeonVisualContext`가 위 값을 함께 제공한다. 비주얼 카탈로그는 raw elevation의 부호로
  깊이/단차를 추론하지 않고 `DepthIndex`와 `LocalHeight`를 각각 사용한다.
  - `DepthBand`는 **진행 지수** 기준으로 1~3번째 `Shallow`, 4~6번째 `Mid`, 7~9번째 `Deep`,
    10번째+ `Boss`로 고정한다(경계 상수는 `DungeonDepthBandRules`). 열거자 이름은 코드/JSON 키로
    남기고 **화면·리포트에는 방향 중립어**(초반/중반/후반/보스)를 쓴다 — `Shallow` 계열 어휘는
    하강 던전 전용이라 상승·`Inward`에서 거짓이 된다.
    깊이별 변주 슬롯을 고르는 축이며 공통 톤 자체를 대체하지 않는다.
  - 모든 깊이의 기준 표면색은 `project-c-torchstone.gpl` 18색의
    `ProjectCEnvironmentCatalog` 런타임 역할색이다.
    같은 구간 안 단차는 `LocalHeight`로만 돌출 두께와 같은 석재군의 명도 신호를 더한다.
- 구현 규칙: `DungeonHeightModel`이 **elevation 4칸을 던전 한 층**으로 묶는다.
  - B1(floor 0) = e0..e3, B2(floor -1) = e-4..e-1, B3(floor -2) = e-8..e-5.
  - 음수 elevation도 floor/local height 왕복 변환이 정확해야 한다.
- 같은 층의 높이 변화는 인접 `Stairs`를 통해 ±1만 허용한다.
- 던전 층 이동은 `GridMap.Connect()`의 명시적 양방향 링크로 `StairsUp ↔ StairsDown`을 연결한다.
- 시뮬레이션은 플레이어가 있는 한 층만 활성화한다.
- 던전 표시는 두 모드로 분리한다.
  - `PLAY FOV`: 현재 층은 `Visible / Explored / Unknown`. 닫힌 문은 문 자체까지만 보이고 뒤쪽 전파를 막는다.
  - `DEBUG ALL`: 모든 층·방·문을 표시하고 층 사이를 작은 간격으로 벌려 생성 구조와 정렬을 검사한다.
- PLAY에서 다른 층의 `Explored` 기록은 미니맵/세이브에는 유지하지만 월드 지오메트리에는 표시하지 않는다. 실제 `Hole`·개구부를 현재 위치에서 볼 수 있을 때만 반대편 국소 범위를 반투명 표시한다.
- 수직 이동은 네 종류로 분리한다: `Stairs`는 같은 던전 층 안에서 걸어서 통과하는 elevation 이동, `Ladder`는 같은 층의 두 높이를 명시적 링크로 잇고 그 위에서 탭/Space로 사용, `StairsUp/Down`은 진입 즉시 반대편 링크까지 한 행동으로 소비하는 활성 던전 층 전환, `Hole`은 낙하와 양방향 시야가 가능한 실제 개구부다.
- **사다리는 계단의 리스킨이 아니다.** 세 줄로 가른다 — 높이: 계단 ±1 단만 / 사다리 여러 단.
  통과: 계단 걸어서(A\*) / 사다리 **링크로만**. 몬스터: 계단 전부 / 사다리 **오를 수 있는 종만**.
  - `GridPathfinder`의 걷기 인접 규칙에서 `Ladder`를 뺐다. 사다리 칸에 **걸어 올라서는 것은 그대로**
    되고 막히는 것은 "타고 오르기"다. 링크는 `canClimb` 인자가 연다.
  - 플레이어가 사다리를 목적지로 누른 첫 입력은 발판에 도착해 **부착하는 데서 끝난다**.
    그 위에서 캐릭터를 다시 누르거나 Space를 입력해야 링크를 탄다. 층 전환 계단처럼 도착과 통과를
    한 행동으로 합치지 않는다.
  - `canClimb` **기본값은 true**다 — 호출부 대부분이 플레이어 이동이거나 도달성 검사라 그쪽이
    정상값이고, 덕분에 기존 도달성 불변식이 그대로 통과한다. 몬스터만 자기 아키타입 값을 넘긴다.
  - `MonsterArchetype.CanClimb`의 **기본값은 false**다. 새 아키타입이 조용히 전부 오르면 이 축이
    죽는다. 인간형(약탈자·투석 약탈자)만 오르고 기계·무정형(경비 드론·슬러지)은 못 오른다 —
    **실루엣과 일치**시켜 배우지 않아도 읽히며, 그래서 캐치워크가 드론에 대한 피난처가 된다.
  - 층 전환 계단 링크는 어느 쪽 끝도 사다리가 아니라 이 제한에 걸리지 않는다.
    걸리게 하면 못 오르는 적이 자기 층에 갇힌다.
  - 캐치워크가 있는 층은 사다리가 바닥(+0) → 캐치워크(+2)를 **곧장** 잇고 중간 발판(+1)은
    링크에서 뺀다(시각적 레일로 남는다). 계단이 ±1만 담당하므로 이 대비가 **"높은 곳은
    사다리로만"을 데이터로 성립**시킨다.
- 사다리 월드 오브젝트는 실제 elevation 차이와 타일 높이로 길이를 계산해 두 착지면 사이에만 걸친다. 디버그 전체 보기에서도 활성 층의 현재 도달 가능한 랜드마크만 표시하고, 층 전환 링크는 개구부처럼 샤프트로 그리지 않는다.
- `StairsUp/Down`은 PLAY에서 다른 층을 노출하거나 점선 샤프트를 그리지 않는다. 전체 링크 구조는 `DEBUG ALL`에서만 표시한다.
- 발견된 `Hole`은 **빛이 없는 허공**으로 읽힌다. PLAY에서는 짙은 개구부(어두운 윤곽 + 중심으로 갈수록 짙은 보이드)와 입구가 짙고 착지로 갈수록 옅어지는 **어두운 보이드 기둥**, 착지 칸의 희미한 표식만 남기며, 이들은 전부 **착지 칸 기준 액터 아래로 정렬**돼 적/아이템/플레이어를 가리지 않는다. 청록 점선 샤프트와 입구 링은 `DEBUG ALL` 전용 진단 표시다. 위에서는 착지점 주변을 내려다보고, 아래에서는 같은 개구부 주변을 올려다볼 수 있다.
- PLAY의 개구부 반대편 조각은 **반대편 층에서 FOV를 한 번 더 돌린 결과**를 현재 층보다 위/아래로 조금 더 벌린 컷어웨이로 표시한다. 전체 층은 노출하지 않는다.
  - **정사각 박스가 아니다.** 예전에는 착지점 중심 체비셰프 반경 안을 전부 넣고 **차폐를 아예 보지 않아** 벽 뒤와 닫힌 문 뒤 방까지 드러났다 — `GridVisibility`의 "void=불투명, 닫힌 문 뒤 방은 Unknown" 불변식과 정면으로 충돌한다. 그래서 문제는 크기가 아니라 방식이었고, 반경만 키우면 문 불변식이 더 크게 깨진다.
  - 같은 셰도우캐스팅을 물려받으므로 벽 뒤는 안 보이고 열린 공간은 오히려 더 넓게 보인다. 비용은 층 하나 FOV 1회.
  - **반경 상한은 남긴다**(1~6, 기본 4). 개구부 너머가 무한히 보이면 기둥 3(제한된 시야)이 무너진다. 이 값은 이제 "박스 크기"가 아니라 **FOV 사거리**이며, 플레이어 시야(6)보다 짧게 둬서 개구부 너머는 "엿보는" 정보로 남는다. 필드 기본값만 바꾸면 씬 직렬화 값이 덮어쓰므로 씬 값도 함께 올린다.
- 수직 수단은 색 범례를 외우게 하지 않는다. 계단은 단차 발판+`WALK`, 사다리는 세워진 레일+`CLIMB`, 층 전환은 어두운 아치+`Bn ▲/▼`, 개구부는 깨진 테두리+반대편 층 표지로 월드에서 직접 읽힌다.
- 해당 종류가 시야에 처음 들어온 순간 `VerticalRouteCue`를 1회 발생시켜 7초짜리 비차단 발견 카드를 보여준다. 카드 문장은 생김새·조작·목적지를 한 문장으로 연결하며, 플레이어가 사다리/층 전환 위에 서면 하단 HUD도 현재 행동을 우선 표시한다.
- 화면 좌표 = 아이소 변환 + elevation 높이 반영. **정렬 우선순위도 elevation 기반** (`IsoGrid`에 집중).
- 시점 회전은 카메라 Transform을 돌리지 않고 `IsoGrid`가 회전 중심 기준으로 `(x, y)`를 90도 단위 투영한다.
  - `GridToWorld`, `WorldToGrid`, `SortingOrder`가 같은 `viewQuarterTurns(0..3)`를 사용한다.
  - 회전 시 타일/액터/소품을 다시 배치하고, 현재 앞쪽 두 변은 열어 두며 뒤쪽 두 변의 벽만 다시 만든다.
  - 2D 스프라이트를 한 장만 쓰는 프로토타입 방식이며, 최종 캐릭터는 같은 회전 이벤트로 4방향 스프라이트를 선택한다.
- **렌더링 높이 ≠ 시뮬레이션 범위** 분리 (성능).

## 원정지 진행 / 보스 출구

- `DungeonCatalog`가 던전별 `FloorCount`, seed, 선택 보스, 진행 방향, 지역 프로파일을 소유한다.
  **원정지는 하나가 아니다** — 지금 열려 있는 곳이 둘이고, 규칙은 전부 던전 데이터를 탄다.
  - **폐병원**(`forgotten-catacombs`, 상승) 10개 층. **표기:
    `B2 → B1 → 1F → … → 8F(보스) → 옥상(출구)`** (GDD §10.1). 진행 지수(내부 0~9)와
    층 라벨(표시)은 분리한다. 구간 이름은 방향 중립어 **초반/중반/후반/보스**를 쓴다 —
    `Shallow/Mid/Deep`은 하강 던전 전용 어휘라 쓰지 않는다.
  - **침수된 금고**(`flooded-vault`, `Inward`) 10구역. 고도가 진행 축이 아니라 라벨이
    `1구역`~`10구역`이고(`DungeonDirectionRules.FloorLabelFor`), **보스가 없어 최심부 출구가
    처음부터 열려 있다**. 지역 프로파일은 `Flooded`(웅덩이 80~90% · 합선 드론 등장)이며
    엘리베이터는 놓지 않는다(`ElevatorShaftRules.AppliesTo`가 `Inward`를 제외한다).
  - **코드 ID·seed·층 수는 유지한다**(리스킨 프로파일 A 원칙). 표시 문자열만 교체하며,
    상승 구조로의 실제 생성기 전환은 별도 작업이다(`ROADMAP.md` 참조).
- 보스가 있는 던전은 최상층의 일반 적 스폰 후보 중 입구와 가장 먼 칸을
  `DungeonBossRules.TrySelectSpawn()`으로 골라 `감시자(GraveWarden)`를 배치한다. 보스는 일반 적보다
  큰 실루엣·금색 틴트·머리 위 표식과 화면 상단 전용 체력바로 구분한다.
- **보스 접근 전조는 방향을 탄다**(`DungeonBossArenaRules.TryApproachCue`). 아레나 바로 앞 층에
  들어서면 한 번 띄우며 문구가 갈린다: 상승 "천장 너머가 낮게 울린다 — 한 층 위에서",
  하강 "바닥이 낮게 울린다 — 한 층 아래에서", `Inward` "울림이 벽을 타고 번진다 — 다음 구역에서".
  예전에는 "한 층 아래"로 고정이라 상승 던전에서 정반대를 가리켰다 — **규칙은 방향을 타지 않아도
  안내 문구는 반드시 탄다**(`FallMeaningHint`와 같은 규약). 이미 처치했거나 보스가 없으면 알리지 않는다.
- 최심층 도착은 그 자체로 승리 조건이 아니다. 출구 개방 판정은
  `DungeonBossRules.CanUseExit(dungeon, bossDefeated)` = `Boss == null || bossDefeated` 하나다.
  - 보스가 **있는** 던전: 보스 생존 중 링크 없는 진출 계단은 붉은 봉인으로 막히고, 탭/Space 시
    봉인 원인을 즉시 안내한다. 처치 후 봉인이 청록색으로 바뀌고 펄스·HUD·상태 메시지가
    출구 해금을 동시에 알린다.
  - 보스가 **없는** 던전: 봉인 자체가 없다. HUD 표기도 갈라서 `HasBoss`면 `봉인 해제된 출구`,
    아니면 `최심부 출구`로 부른다 — 있지도 않았던 봉인을 "풀렸다"고 말하지 않기 위해서다.
- 최종 출구에서 `던전 정복`을 선택해야 전리품 정산, 런 세이브 삭제, 승리가 확정된다.
  `생환하기`는 기존 extraction 규칙을 유지한다.
- `RunSaveData`는 `dungeonId`, `stageCount`, `bossDefeated`를 저장한다. 보스 처치 직후 체크포인트를
  다시 기록해 로비를 거쳐 이어해도 보스가 부활하거나 출구가 재봉인되지 않는다.
- PlayMode 스모크 테스트는 격리된 개발 저장 루트에서
  `MainMenu → Hub → Dungeon B1/B10 → boss → exit` 전체 흐름을 검증한다.

## 엘리베이터 (복귀 동선)

- `ElevatorShaftRules`가 SSOT. **던전당 한 대**(`ShaftsPerDungeon = 1`)이며 탑승구는 보스 아레나
  **바로 앞 층**(`EntranceProgressIndex = floorCount - 2`), 도착은 **진행 지수 1**이다.
  여러 대면 "아무 층에서나 복귀"가 되어 진행의 무게가 사라지고, 탑승구가 보스로 가는 길목에
  있어야 **멈춰 있는 것을 먼저 본다** — 그래야 전원이 들어오는 게 사건이 된다.
- 도착이 첫 층(0)이 아니라 1인 이유: 첫 층 입구 방은 진입 연출과 세이브 복원이 얽혀 있어
  특수 타일을 얹지 않는다.
- **전원은 보스 처치로 들어온다**(`IsPowered(hasBoss, bossDefeated)` = `!hasBoss || bossDefeated`).
  층마다 자유롭게 되돌아갈 수 있으면 진행의 긴장이 사라지므로 게이트를 둔다. 사용 횟수를 세지 않고
  **상태 하나(전원)**로 다루므로 UI·세이브도 단순하다. 보스가 없는 던전은 처음부터 움직이는 것으로 본다.
- **생성기는 설비만 놓고 링크를 만들지 않는다.** 링크가 곧 "움직인다"이며, 없는 동안은
  경로 탐색도 이 칸을 지름길로 쓰지 않는다. 전원이 들어오는 순간 Gameplay가 `Connect`를 넣는다
  (보스 처치 직후와 **이어하기 복원** 양쪽에서 호출되고, 여러 번 불려도 안전하다).
- **복귀 전용 단방향이다.** 진행 방향으로 태우면 계단을 건너뛰는 지름길이 되어 페이싱이 무너진다.
  보스를 잡은 뒤에는 최종 출구가 이미 열려 있으므로 엘리베이터는 **선택**이다 — 지나친 층의
  파밍(기둥 4)을 회수하러 다녀오는 길이지 강제 동선이 아니다.
- **낙하로 대신하지 않는 이유**: 낙뎀 곡선상 3층 자유낙하는 12이고 원정자 HP는 10이다.
  완충 부츠(+2칸)를 껴도 9라 탈출이 아니라 자살이다. 그래서 "탑승"으로 풀고 낙뎀 곡선은 건드리지 않는다.
- **`Inward` 던전에는 없다**(`AppliesTo`). 거기서는 오르내림이 진행이 아니라고 선언했으므로
  (라벨도 `1구역`) 층을 관통하는 승강 연출이 화면과 어긋난다. 층이 너무 적어 탑승구와 도착층이
  겹치는 던전도 제외한다(`AppliesToDungeon`, 최소 4층).

## 시야 / 안개 (FOV) — §5.2

- 타일 상태: `Unknown` / `Explored` / `Visible`.
- 알고리즘: **Recursive Shadowcasting (구현됨, `GridVisibility`)** — (x,y) 2D 8옥탄트 캐스팅 + 컬럼별 span 해석(`SightRules.ViewColumn`). 반경은 체비셰프.
  - **컬럼은 높이맵이 아니라 span이다**: 눈높이 이하의 지면과 눈높이 위의 머리 위 구조물(캐치워크·메자닌)을 각각 결과에 넣는다. 캐치워크 아래 바닥도 보이고, 캐치워크 위에 서면 눈높이가 올라가 아래가 이어져 보인다. 지면보다 아래 타일은 덮여서 나오지 않는다.
  - **void(타일 없는 컬럼) = 불투명.** 이 던전은 방 경계를 벽 타일이 아니라 타일 부재로 표현하므로(벽은 비주얼 전용), 이 규칙이 "닫힌 문 뒤 방은 Unknown" 불변식의 핵심.
  - 닫힌 문/벽은 그 칸까지만 보이고 너머 차단. **Hole/약한 바닥/계단은 투과** (`SightRules.HasLineOfSight`와 동일 기준 — 원거리/폭탄과 시야가 일치).
  - 눈높이보다 1단을 초과해 높은 표면은 벽처럼 너머를 막는다(`HeightBlockThreshold`). 1단(raised)은 막지 않는다.
  - **수직(같은 컬럼) 시야는 실제 개구부만 통과한다** — 허공은 통로, 온전한 바닥은 차단(`TileData.BlocksVerticalSight`).
    Hole 국소 미리보기(`SightRules.ViewFromFloor`)도 이 판정을 거치므로 개구부와 착지 사이에 바닥이 끼면 보이지 않는다.
- 층 규칙: 플레이어 층 일반 FOV / 아래층은 **구멍(Hole)을 포털 삼아** 반경만 Visible / 위층은 뚫린 곳 아래에서만.
- 표현: tint + alpha.
- `PLAY FOV`의 미탐색 영역은 실제 방·복도 모양 대신 층 생성 범위 전체를 덮는 어두운 아이소 안개 배경으로 표시한다. 카메라 void와 색·외곽선을 달리해 플레이 영역은 읽히되, 아직 발견하지 않은 구조는 노출하지 않는다. 이 배경은 입력 대상이 아니며 실제 이동 가능 여부는 항상 `GridMap.Has()`가 결정한다.
- 적 전투 피드백도 같은 FOV를 따른다. 시야 밖 적의 피해 플로팅·플래시·사망 문구는 숨기고, 폭발 적중 수는 보이는 대상만 센다. 전투 결과와 처치 전적 자체는 그대로 반영한다 (`EnemyPresentationRules`).

## 창문 (수평 시야 포털 → 통로)

- `WindowRules`가 상태 전이의 SSOT다. **온전한 창문(`Window`)은 이동을 막고 시야는 통과시킨다** —
  `BlocksSight`에 들어가지 않으므로 방 안에서 바깥을 내다볼 수 있고, `IsWalkable`이 아니므로
  넘어갈 수는 없다. 벽이 "타일 부재(void)=불투명"인 이 던전에서 **바깥을 보여 주는 유일한 벽**이다.
- **깨면 통로가 된다.** `WindowBroken`은 단단한 바닥이자 걸을 수 있는 칸이고 **다시 닫을 수 없다** —
  되돌릴 수 있으면 "깨뜨렸다"가 사건이 아니라 토글이 된다.
- 깨는 원인은 지금 **폭발 하나**다(`Interactions`의 3×3 블라스트가 `TryBreak`로 수렴). 원인이 늘어도
  전이는 이 함수 하나를 거친다 — 갈라지면 "어떤 창은 안 깨진다"가 생긴다.
- **창문은 층당 하나이고 자리가 규칙이다**(`PlaceWindows`, RNG 미사용): 안쪽이 방 바닥이고,
  창 자리가 원래 void(외벽)이며, **창밖도 허공이고 그 아래가 정확히 한 층 아래 걷는 바닥**인
  칸에만 놓는다. 착지 검증은 개구부와 같은 판정을 쓴다.
- 그래서 **도달성 불변식이 흔들리지 않는다** — 원래 벽이던 자리를 창으로 바꿀 뿐이고, 깨도
  열리는 곳은 허공이다. 대신 대형 렌치 넉백·폭발 넉백이 창밖으로 밀면 그대로 `TryFall`이다.
  상승 던전에서는 이것이 전진이 아니라 **후퇴·탈출**이다(아래 "낙하" 참조).

## 지형·층간 상호작용 & 낙하 — §5.3

- 모든 낙하 트리거는 `TryFall()` 하나로 수렴: 넉백→구멍, 약한 바닥 붕괴, 함정/밀 수 있는 오브젝트.
- 처리: 아래로 첫 단단한 바닥 탐색 → 낙하 층수 → 낙뎀(누적 곡선) → 착지점 적 있으면 양쪽 데미지.
- **플레이어에도 동일 규칙 적용** (실수 낙하 가능 = 긴장).
- 구현 (M4, `FallRules`/`KnockbackRules`): 낙뎀은 **칸 기준 가속 곡선**(`DamageForDrop`)이다 —
  `eff = max(0, 낙차 칸수 − 안전 낙하 높이)`이고 데미지 = `round((eff/EPF) × (eff/EPF + 1))`.
  EPF(층당 elevation)=4라 층 단위 값은 종전과 같고(1층 2·2층 6·3층 12) **층 안 낙하(2~3칸)도 작게 반영된다**.
  층 단위 `DamageForFloors`는 프로덕션 경로가 부르지 않는 **기준 곡선(오라클)**이라 남는다 —
  칸 기준 곡선이 여전히 2/6/12를 재현하는지 `FallRulesTests`가 이 값과 대조한다(호출부가 없다고 지우면 그 대조가 사라진다).
  착지점에 산 점유자가 있으면 양쪽 낙뎀 후 낙하자는 인접 빈 칸으로 밀려난다. 넉백은 폭발 중심 반대 우세 축 1칸 — 벽/닫힌 문/점유는 무효, 구멍/허공이면 TryFall. 약한 바닥은 밟거나(이동) 충격(넉백 착지)으로 붕괴해 구멍이 된다. 폭발 반경 안의 폭발통은 유폭해 연쇄 폭발한다.

## 전투 (기본) — §5.4

- 턴제: 플레이어 1행동 → 몬스터 1행동.
- 근접(**반드시 인접**) / 원거리(투사체 궤적) / 넉백. HP + 간단 스탯.
- 검증 전투는 HUD에서 `MELEE / RANGED`를 전환한다. 근접은 적 인접 칸까지 자동 접근하며 한 단(≤1) 위·아래도 친다(위에서 내려치면 +1). 원거리는 도달 비용(맨해튼+|Δe|)이 사거리 안이고 높이 인식 시야선(`SightRules`)이 뚫려야 명중한다. 닫힌 문, 벽, 빈 타일은 사격선을 차단한다.
- 시체는 기본 3턴간 HP 바 없이 회색으로 남아 매 턴 흐려진다. 수명이 끝나면 씬 오브젝트와 적 목록에서 함께 제거되어 월드 탭 보정에도 더는 잡히지 않는다.
- **원거리는 근접보다 약하고 짧다** (기본 피해 1·사거리 4 vs 근접 3): 지각이 플레이어 FOV 대칭 + 이동속도 동일 구조라, 무비용 원거리가 근접과 같은 피해면 접근하는 몬스터를 전부 무피해 카이팅으로 잡는다(밸런스 시뮬로 확인). 원거리는 마무리/견제 수단.
  수치의 SSOT는 `SurvivorProfile`(HP 10·근접 3·원거리 1) 하나다 — 씬 인스펙터의 `playerAttack` 기본값은
  플레이 시작 시 덮어써지는 에디터 미리보기 값이라 여기 옮겨 적지 않는다.
- 낙하는 하강 수단으로도 사용 가능 (계단 대신 뛰어내리기).
- Hole을 탭하면 적 점유 칸을 피해 인접 칸으로 접근한 뒤 `FindLandingBelow()`의 첫 단단한 바닥으로 낙하한다. 현재 프로토타입은 이동만 처리하며 낙뎀·충돌 피해는 M4 `TryFall()`에 통합한다.

## 상태이상 & 요소 반응 — §5.5

- 상태이상: 화상(Burn) / 빙결(Freeze) / 중독(Poison) / 폭발(Explosion) + 타일 원소 젖음·감전
  (확장으로 남은 것은 **기름 타일**뿐이다 — 기름은 아직 아이템이고 생성기가 깔지 않는다).
- 반응 예: 불+기름=확산·폭발, 물/젖음+빙결=광역 결빙, 젖음+감전=광역뎀, 화상+폭발통=연쇄.
- 구현: 타일/엔티티에 **상태 플래그 + 지속턴**, 매 턴 평가하는 **반응 테이블(데이터화)**.
- 구현 (M4, `StatusEffects`/`StatusReactions`): 참가자별 상태 집합 — 화상=턴당 틱뎀, 빙결=턴 스킵, 재부여는 지속 연장. 반응 테이블 첫 항목은 불↔얼음 상쇄(해동/진화). 폭발 생존자는 화상 2턴. 턴 파이프라인은 **활성화 → 상태이상 틱 → Decide → 실행**이며 휴면(컬링) 중에는 틱도 멈춘다.
- **중독**(`StatusKind.Poison`): 턴당 1 틱뎀(`PoisonDamagePerTurn`)이며 **화염/빙결과 무관하게
  독립 지속한다** — 상쇄 테이블에 넣지 않은 이유는 불로도 얼음으로도 독을 지우게 하면
  "슬러지에 물리면 곤란하다"는 압박이 소모품 하나로 사라지기 때문이다.
  누출 오염 슬러지가 근접 명중 시 2턴을 건다.
- **젖은 칸 위에서는 화상이 꺼진다**(`Tick(onWetTile)`) — 물+불의 타일 쪽 반응이다.
  웅덩이가 피난처가 되므로 물 지역에서 불이 약해지는 것이 지역 정체성으로도 읽힌다.
- **감전**(`ShockRules.Discharge`/`DischargeDetailed`): 명중점 3×3 직격(마른 바닥 포함) +
  블라스트가 닿은 젖은 웅덩이를 4방향으로 통전시켜 그 위 대상 전원을 지진다.
  **한 대상은 한 번만** 맞는다(직격과 통전이 겹쳐도 이중 피해가 아니다).
  웅덩이 확산은 결빙(`WaterRules.ChainFreeze`)과 **같은 함수를 공유**한다(`WetPoolFlood.Collect`) —
  기준이 갈리면 "얼릴 땐 이어지는데 지질 땐 안 이어지는" 물웅덩이가 생긴다.
  적을 먼저 물로 몰아넣는 셋업 전술의 후반 도구이고, 합선 드론이 이 축을 플레이어에게 되돌린다.
- 전투 표현은 `CombatPresentationRules`가 source를 물리/화염/냉기/강타로 분류하고,
  Gameplay가 공격자 돌진·대상 스쿼시/다중 플래시·픽셀 버스트·감쇠 카메라 흔들림으로 번역한다.
- 화상은 주황 불꽃 고리+따뜻한 몸 틴트, 빙결은 청록 결정 고리+차가운 몸 틴트다.
  `StatusEffects.Apply()`의 `Applied / Refreshed / CancelledOpposite` 결과로 부여·연장·상쇄 팝업을 구분한다.
- 적의 순간 타격과 지속 상태 FX 모두 `IsEnemyVisibleToPlayer()`를 통과해야 생성/활성화된다.
  디버그 패널의 `피해 1 / 화상 FX / 빙결 FX`로 화면 크기별 연출을 즉시 검증할 수 있다.

## 파밍 & 조합 — §5.6

- 진행 중 자원 수집 → 조합으로 소모품/장비 제작 (예: 기름+병=화염병) → 메타 프로그레션 연결.

## 몬스터 AI & 활성화/컬링 (성능 핵심) ⭐ — §5.7

- **활성 반경**: 플레이어 주변 + 같은 방/시야 내 몬스터만 "활성" → 매 턴 사고. 나머지는 휴면(간헐 갱신).
- 다층: 보이는 층이라도 구멍 근처 등 상호작용 가능한 몬스터만 활성.
- 스폰: 절차생성 배치 규칙 + 진행 중 추가 스폰 (난이도·깊이 연동).
- 행동: 단순 상태머신(순찰→추격→공격→도주)부터, 필요 시 유틸리티 AI로 확장.
- 구현 규칙 (M2, `MonsterBrain`/`MonsterActivation`/`MonsterArchetype`):
  - 파이프라인: **활성화 판정 → (M4: 상태이상 틱 자리) → Decide(의도 반환) → 실행**. 브레인은 Wait/Step/OpenDoor/Attack "의도"만 반환하고 위치·타일·연출 변경은 Gameplay가 실행 — M4 낙하(TryFall)·상태이상이 이 파이프라인에 끼어든다.
  - 지각 = **플레이어 FOV의 대칭**(`seenByPlayer` 콜백) + 어그로 반경(체비셰프). 같은 턴 다중 이동은 플레이어와 가까운 순으로 순차 처리해 점유 충돌을 없앤다.
  - 몬스터는 **추격 중에만 닫힌 문을 연다**(행동 1회). 순찰 중에는 열지 않으므로 "문 뒤 스폰" 구조가 유지된다. 시야를 잃으면 마지막 목격 지점까지 수색 후 순찰 복귀.
  - 활성화 = 같은 층 && 활성 반경(FOV+2). 규칙 목록 형태로 유지 — 층간 규칙("보이는 구멍 인접 아래층 몬스터")은 추후 추가.
- 구현 규칙 (`MonsterRoster`): 일반 몬스터 5종 — 약탈자(공2·빈사 시 도주), 낡은 경비 드론(단단·비도주), 누출 오염 슬러지(약함·넓은 배회·근접 명중 시 중독 2턴), **투석 약탈자(첫 사수: 사거리 4·원거리 피해 2·근접 피해 1, 2칸 안으로 붙으면 물러섬)**, **합선 드론**. 스탯·밴드 혼합표는 roster/밴드 프로파일 한 곳에.
  - **합선 드론**(`ArcDrone`): HP5·근접1·원거리 2·사거리 4·2칸 안이면 물러섬으로 투석 약탈자와
    같은 사수 골격이지만, 원거리 효과가 `ConductiveShock`이라 **명중점 3×3 직격 + 닿은 웅덩이
    전체를 통전시켜 다른 적까지 지진다**. 물 위에서 안전하게 거리를 재던 교환을 깨는 것이 존재 이유다.
    **침수된 금고 전용** — 지역 축에서만 등장 가중치를 주므로(`DungeonBandProfile.ArcDroneWeight`:
    침수 중반 20 / 후반·보스 25, 다른 지역과 침수 초반은 0) 첫 구간은 종전과 같고 물 지역에서만 얼굴이 바뀐다.
  **등반 가능 여부(`CanClimb`)도 여기 있다** — 인간형 둘(약탈자·투석 약탈자)만 true, 기계·무정형
  (경비 드론·슬러지·합선 드론)은 false. 기본값이 false라 새 아키타입은 명시하지 않으면 못 오른다.
- **원거리 교전**: 사수는 붙기 전에 쏜다 — 거리 벌리기 → 사격 → 사선 잡기 순으로 결정하고, 셋 다 안 되면 일반 추격으로 넘어간다. 판정(사거리 예산에 높이차 과금·시야선)은 플레이어와 같은 `CombatRules`/`SightRules`를 공유한다. 플레이어의 무피해 카이팅에 대한 반대 압력이며, 엄폐·높이·돌진이 여기서 의미를 갖는다. **진행 중 추가 스폰**: 12턴 간격, 활성 층 몬스터가 상한(`4 + AreaSpawnBonus(층 면적)`, 기본 13×13에서 4) 미만일 때 플레이어 시야 밖 스폰 지점에 깊이 혼합으로 1마리. 상한이 고정값이 아니라 **생성기 밀도 보정과 같은 함수**를 쓰는 이유는 층을 키웠을 때만 방이 텅 비는 것을 막기 위해서다.
- **하행 계단 경비병**: 북쪽 방 스폰만으로는 완주 동선(남쪽 방→하행 계단)이 전투를 완전히 우회한다(시뮬로 발견). 하행 계단 인접(체비셰프 3)에 1+depth 마리를 추가 배치 — 깊을수록 무거운 관문. 하행 방은 도착 방과 항상 달라 "문 열기 전 차단" 스폰 불변식은 유지된다. **최심층 아레나는 예외로 통째로 건너뛴다**(`DungeonBossArenaRules.IsArenaFloor`) — 경비병 무리 대신 보스 1:1 구도를 비운다(캐치워크를 놓지 않는 것과 같은 이유).

## 아이템 / 던전 생성 — §5.8

- 무기, 소모품(폭탄=바닥 파괴 등), 열쇠, 조합 재료.
- 구현된 소모품 규칙 (`Items.cs`): **물약** = HP 회복, 행동 1회 소비. **폭탄** = 사거리·시야선 확보된 단단한 타일에 투척, 같은 elevation 3×3 피해(던진 본인 포함 — 자폭 가능) + 화상 + 넉백, 빈 약한 바닥 붕괴·폭발통 유폭. **냉기 폭탄** = 낮은 피해 + 빙결 2턴, 폭발통은 유폭하지 않음(불이 아님). 낙하 처리는 `TryFall()`로 수렴.
- **3×3 블라스트 범위 판정은 `BombRules.ForEachBlastCell` 하나로 수렴한다.** 폭발 피해·기름 발화·물 증발·감전 직격·비밀문 공개·유리 파괴가 전부 같은 칸 집합을 본다 — 범위가 갈리면 "폭탄은 닿았는데 비밀문은 안 열린다" 같은 설명 불가능한 경계가 생긴다.
- **투척 조준은 숫자 설명보다 월드 범위를 먼저 보여준다.** 폭탄·냉기 폭탄·기름 병은
  `BombRules.ForEachThrowTarget`이 반환한 실제 유효 칸 중 현재 FOV에 보이는 칸만 바닥 마커로
  표시한다. 투척 단검은 `CombatRules`의 사거리·시야선이 성립하는 보이는 적 칸만 표시한다.
  Unknown·벽 뒤·다른 elevation을 표시해 제한된 시야 정보를 누설하지 않는다.
- 절차 생성 (룸-앤-코리더 또는 BSP) + 높이차(계단/경사) 배치.
- 생성기는 층마다 **방 3개(+확률적 막다른 분기 방) → 1칸 복도 → 복도 목의 문** 그래프를 유지한 채, 방 크기/위치·복도·문·내부 계단·구멍·적 스폰을 **seed로 변형**한다. 같은 seed는 같은 던전을 재현한다.
- 생성 불변식 (EditMode 테스트로 고정): 문을 모두 열면 모든 walkable 타일이 입구에서 도달 가능하고, 문을 닫으면 북쪽 방이 차단된다. 개구부의 **모든 칸**이 **정확히 한 층 아래의 walkable 칸**에 착지하며, 윗층 개구부의 착지 칸을 다시 뚫지 않는다(2층 관통 방지). 아래층 북쪽 방은 윗층과 기둥이 겹치게 제약해 개구부 후보가 항상 남는다.
- **개구부는 점이 아니다 — 최대 3칸까지 자란다.** 1칸짜리는 정찰 창구·전술 무대·공간의 인상·지름길 네 역할을 전부 얕게 수행했고, 특히 넉백으로 떨어뜨리는 것이 운에 가까웠다.
  - **2×2 를 강제하지 않는다.** 북쪽 방 밴드는 최소 크기 던전에서 아주 얕고 Y축 층간 겹침은 보장되지 않는다(X축만 제약한다). 모양을 강제하면 후보가 0이 되거나 방이 잘려 도달성이 깨진다.
  - 대신 앵커 한 칸을 고른 뒤 **한 칸씩 자라며, 방이 잘리는 칸은 고르지 않고 거기서 멈춘다**(`KeepsUpperRoomConnected` 플러드 필). 결과는 seed마다 2~3칸이고 자리가 없으면 1칸으로 끝난다.
  - 데이터 모델은 목록이다: `DungeonFloorInfo.HoleTiles`가 1급이고 `Hole`은 **대표 칸**으로 남는다(샤프트 연출·엘리베이터 충돌처럼 한 점이면 충분한 곳용). 집합 판정이 필요한 두 곳만 목록을 쓴다 — 2층 관통 금지(윗층 개구부 **전체**와 비교)와 약한 바닥(4방 인접 → 개구부 **둘레**).
  - **개구부와 약한 바닥은 같은 판정 함수를 쓴다.** 약한 바닥은 밟으면 개구부가 되므로 기준이 갈리면 붕괴가 불변식을 깬다.
  - **RNG 스트림을 밀지 않는다** — 성장 루프가 난수를 쓰지 않아 뽑는 횟수가 그대로다(앵커 1 + 약한 바닥 1). 그래서 방·계단·적·아이템 배치는 동일하고 달라진 것은 개구부에 붙은 칸들뿐이다.
  - 추가 계약 테스트: 개구부의 모든 칸이 착지 규칙을 지킬 것(넓히면서 한 칸이라도 새면 그게 2층 관통이다), 칸들이 **한 덩어리**로 이어질 것(흩어지면 "개구부 하나"라는 전제가 깨진다), 상한을 넘지 않을 것.
- 스폰 규칙: **일반 적 스폰은 문 뒤(북쪽 방)에만** 둔다 — 입구 방에 두면 진입 즉시 인접 전투가 강제되고 문 차단 불변식도 깨진다. 수는 `1 + rand(0~1) + 진행 지수/2 + 밴드 보정(ExtraEnemies) + 면적 보정(AreaSpawnBonus)`이 SSOT이며(10층 던전 후반이 6~7마리) 고정 상한이 아니다. 여기에 위의 **하행 계단 경비병**(동/남쪽 방, `1+깊이` 마리)이 더해지므로 "북쪽 방에만"은 **일반 스폰에만 걸리는 불변식**이다. **아이템**(물약/폭탄)은 북쪽·동쪽 방 빈 바닥에 1~2개, 막다른 분기 방에는 보상 1개를 보장한다. 적·아이템·입구·특수 타일은 서로 겹치지 않는다.
- `DoorClosed`는 단단한 바닥이지만 이동·시야를 막는다. 인접 상호작용으로 `DoorOpen`이 되면 이동·시야가 통과한다.
- `SecretDoor`는 벽으로 위장한 별도 타입이다. 일반 문처럼 자동으로 열리지 않으며 인접 조사나
  폭발로 공개된 뒤에만 `SecretPassage`가 된다. 10층 던전은 보스 층과 미구출 동료가 갇힌 층을
  제외한 세 층에 정확히 하나씩 생성한다(후보가 모자라면 그만큼 줄어든다 — 위 "숨은 방" 참조).
- PLAY 시야 계산도 같은 문 상태를 사용한다. 닫힌 문 뒤 방은 Unknown이고, 문을 연 직후 FOV를 다시 계산해 다음 공간을 드러낸다.
- 문 열기와 닫기는 플레이어 행동 1회를 소비한다. 자동 경로가 닫힌 문을 무시하고 통과해서는 안 되며, 상태 전환 때 문짝 접힘·상호작용 버스트·HUD 피드백을 함께 갱신한다.
- 문 비주얼은 정면 사각형을 사용하지 않는다. 통로가 남북이면 동서 평면, 통로가 동서면 남북 평면에 문틀을 세우고 `IsoGrid` 회전에 맞춰 사선 방향을 다시 고른다.
- 이후 확장(진짜 룸-앤-코리더/BSP)에서도 이 연결 그래프와 생성 불변식을 유지한다.

## 크로스플랫폼 (PC/모바일) — §12

- **입력 추상화**: Unity Input System(new)으로 터치/마우스/키보드/게임패드를 액션 단위 매핑. 게임 로직에 플랫폼 분기 금지.
- **월드 탭 경계**: UI 차단 뒤 `GridMap.Has()`로 실제 타일인지 확인한 입력만 게임플레이에 전달한다. 화면의 검은 여백(void)은 미탐색 칸이 아니며, 이동·조준·자동 이동 취소를 일으키지 않는다. 벽은 맵 안의 타일이므로 전달한 뒤 이동 불가 피드백을 준다.
- **다층 월드 픽킹**: 모든 elevation 평면을 역산해 존재하는 타일을 고르지 않는다. 실제
  렌더된 아이소 다이아몬드의 `VisualPosition`으로 히트 테스트하고, 겹치면 현재 활성 층
  → 개구부 인접 층 미리보기 → 같은 레이어의 렌더 정렬 순서 순으로 선택한다.
- 호버 부재: 탭=선택, 재탭=실행 2단계 (또는 롱프레스로 정보).
- 조준: 타일 단위 스냅 + 확인 단계 (턴제라 유리).
- UI: 화면 고정 HUD는 UI Toolkit의 `PanelSettings(Scale With Screen Size)`로 화면비 대응, 안전영역(노치). 월드 앵커 UI만 UGUI를 사용한다. 저장 포맷은 플랫폼 독립적으로.
- 카메라: 던전은 플레이어 추적 구도를 유지한다. 고정 크기 허브는 투영된 맵 경계를 기준으로 중심과 직교 카메라 크기를 화면비별 계산해 모든 주요 지점을 노출한다.

## 프런트엔드 씬 흐름

- Build Settings 순서: `MainMenu` → `Hub` → `IsoPrototype`.
- `MainMenu`는 타이틀·원정 복귀·설정만 소유하고, `Hub`는 캠프 월드와 원정지 선택만 소유한다.
- 새 게임 경로는 `MainMenu → Hub → IsoPrototype`이다. 이후 세계관/프롤로그는
  `MainMenuController.EnterCamp()`의 다음 목적지를 별도 스토리 씬으로 바꿔 삽입한다.
- **타이틀은 앱 실행마다 한 번 지나는 문이지 판마다 돌아오는 착지점이 아니다.**
  판이 끝난 뒤의 착지점은 캠프다 — 던전 게임 메뉴의 `로비로 가기`(체크포인트 보존)와
  게임오버의 `캠프로 돌아가기`가 모두 `Hub`로 간다. 게임오버에서 던전 씬을 바로
  리로드하는 재도전 버튼은 두지 않는다: 방금 번 골드·해금·구출한 동료를 못 쓰고
  같은 조건으로 되돌아가는 길이라 "실패도 전진"이라는 루프를 건너뛴다.
- 타이틀 버튼 규칙(`TitleEntryRouting`, 순수 규칙 + EditMode 테스트):
  - `게임 시작`은 **언제나 `Hub`로 간다.** 첫 실행이든 재접속이든 캠프가 시작점이라
    버튼 이름과 목적지를 저장 상태에 따라 흔들지 않는다.
  - `이어하기`는 **던전 중간 저장(층 체크포인트)이 있을 때만 존재하고** `IsoPrototype`로
    직행한다. 없으면 비활성 회색으로 남기지 않고 숨긴다 — 죽은 직후의 회색 `이어하기`는
    정보가 아니라 "원정을 잃었나?"라는 오해다.
- 에디터/개발 빌드는 공용 설정에서 `DevelopmentSaveProfile`을 켤 수 있다.
  이때 `MetaStore`와 `RunSaveStore`는 실제 저장 루트가 아닌
  `persistentDataPath/development-profile/`만 사용한다. 던전 진행 중에는 프로필
  변경과 초기화를 잠가 현재 런과 저장 목적지가 섞이지 않게 한다.
