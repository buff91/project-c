§1 · 기획서 현재 기준

지금의 기획서는 무엇을 약속하는가

한 줄 콘셉트 — 시야에 따라 조금씩 드러나는 다층 아이소메트릭 던전에서, 지형·불·얼음·높이를 전부 무기로 삼아 — 기름에 불을 붙이고, 얼려서 밀어 떨어뜨리고, 바닥을 무너뜨리며 — 싸우는 턴제 로그라이트.

높이차를 앞세우지 않는다(개정). 높이차는 여러 전술 축 중 하나다. 콘셉트가 높이만 가리키면 상태이상·요소 반응·지형 상호작용이 부속품처럼 읽히고, 실제 플레이도 "모든 전투의 답은 밀어 떨어뜨리기"로 수렴할 위험이 있다. 기둥 1과 기둥 2는 대등하다 — 아키텍처가 이미 그렇게 짜여 있다(§4·§5는 서로를 호출하지 않고 TryFall· StatusEffects라는 별도 수렴점을 갖는다).

설계 기둥 — 모든 판단의 기준

1

입체 공간

공간을 전술 자원으로. 층(floor)이 수직의 주 단위이고, 층 내 높이차는 동기 있는 구조물에만 드물게. 낙하는 상호작용의 하나.

FallRules · SightRules · DungeonHeightModel

2

상호작용 & 상태이상

화상·빙결·독·감전 + 기름/물 타일 반응. 전투의 깊이는 여기서 나온다.

StatusEffects · OilRules · WaterRules · ShockRules

3

제한된 시야

Unknown/Explored/Visible 3상태. 정보의 부재가 곧 긴장이며, 그래서 연출·HUD까지 FOV를 탄다.

SightRules · GridVisibility · FloorVisibilityRules

4

파밍 & 조합

6×4 멀티슬롯 백팩 · 레시피 · 익스트랙션. 하드 타이머 대신 배고픔으로 압박.

BackpackRules · CraftingRules · ExtractionRules

창발적 전술은 5번째 기둥이 아니라 위 4개가 충돌해 생기는 결과다 — 목표이자 검증 기준. "적을 얼려 밀어 떨어뜨리기"가 어느 한 시스템에도 하드코딩돼 있지 않은 이유.

v0.3에서 확정된 것 / 아직 안 정한 것

확정

  • 테마 = 포스트 아포칼립스 / 이상 미궁. 설정에 방향성을 두지 않는다 — 미궁은 도시를 잠식했고, 상승·하강·평면은 던전별 정체성
  • 수직성 어휘 = 건물형. 층·계단실·창문·엘리베이터 통로
  • 첫 던전 = 폐병원 상승 10개 층 + 옥상 출구. 지하 던전은 외벽 창문이 성립하지 않아 WindowRules의 절반이 죽는다
  • 진행 방향은 던전별 데이터 — 하강 / 상승 / 진입 깊이(고도가 축이 아님) 셋이 공존한다. 전역 스위치가 아니다
  • 장비는 공격력을 올리지 않고 규칙만 바꾼다 (영구 스탯 강화 제거)
  • 팔레트 18색 고정 · 깊이 변주는 스프라이트 슬롯/구조/광원으로만

미확정

  • 메타 해금 대상의 최종 범위 (레시피 / 시작 장비 / 역할)
  • 단일 영웅 vs 역할제 — 현재는 3영웅이나 프로토는 단순화 방침
  • 후속 던전(침수된 금고·잿불 성채) 개방 조건 = "다른 적"이 선행
  • 보스/최심층 보상 수치 (완주 시간은 목표치를 두지 않기로 확정)
  • 배고픔 단계에 붙일 별도 상태이상

문서 간 드리프트 주의. 기획서 본문(§4.2 조작, §7 기술 스택, §8 마일스톤)은 아직 "모바일 전용" 시점으로 쓰여 있지만, 실제 개발 우선순위는 CLAUDE.md·ROADMAP.md의 PC 우선(모바일 보류)이다. GDD §8 체크박스도 전부 미체크지만 M0~M6은 코드 완료 상태다.

§2 · 아키텍처 계약

모든 코드가 지키는 다섯 줄

UI UXML / USS · UI Toolkit(화면공간) + UGUI(월드 앵커). 상태를 소유하지 않는다.
Gameplay MonoBehaviour · 씬/스프라이트/연출/파일 I/O. Core의 의도를 세계로 번역한다.
Core 순수 C# 규칙 · 좌표·수치·의도만 반환. UnityEngine을 사실상 모른다.

↓ 의존은 언제나 한 방향. Core는 위층의 존재를 모른다.

  1. 로직 ↔ 비주얼 분리 (최상위 규칙). Core는 의도·수치·좌표 목록만 반환하고 씬 변경은 전부 Gameplay가 한다. 크로스-레이어가 필요하면 Core가 콜백(Func/Action)을 인자로 받는다 — 예: MonsterBrainContext.SeenByPlayer.
  2. 정렬 규칙은 IsoGrid 한 곳에. floor(elevation) 우선 + (x+y). 씬에 적용하는 유일한 지점은 GridSortingObject다. "아이소 정렬 지옥" 방지 장치.
  3. 입력 추상화. 터치/마우스/키보드를 IsoTapInput에서 GridPos/액션으로 통일. 게임 로직에 플랫폼 분기 금지(PC 우선 기간에도 유효).
  4. 데이터 중심. 밸런스 수치는 정적 카탈로그에 (MonsterRoster·ItemCatalog·HeroRoster·DungeonCatalog·DungeonBandProfile).
  5. 보이는 층 ≠ 활성 층. 시뮬레이션은 플레이어가 있는 한 층만, 몬스터는 활성 반경 밖이면 휴면.

어셈블리 경계 (asmdef 5개)

ProjectC.Core ← ProjectC.Gameplay · ProjectC.ArtPipeline.Editor · ProjectC.Tests.EditMode · ProjectC.Tests.PlayMode. 경계가 컴파일러로 강제되므로, Core에서 UnityEngine을 부르고 싶어지는 순간이 곧 설계가 틀어지는 순간이다.

네 기둥이 전부 여기 올라탄다. 여기가 흔들리면 기둥 전부가 흔들린다.

3.1 · 공간 기반 — 좌표가 곧 코드의 딕셔너리 키

타입책임결정적 세부
GridPos 논리 좌표 {x, y, elevation} elevation은 연속 높이값(층 번호 아님). 거리 계산은 elevation을 무시한다.
TileData
TileKind		 타일 의미론 15종 + 술어 IsSolidGround/IsWalkable/BlocksSight/CausesFall가 이동·시야·낙하의 불변식을 만든다. 요소 플래그 oiled/wet도 여기.
GridMap 희소 타일 + 링크 그래프 두 종류의 인접성이 공존 — 공간 4-이웃, 그리고 Connect()가 만든 명시적 링크(층 전환·사다리). FindLandingBelow()가 모든 낙하·수직 시야의 원시 연산.
IsoGrid 투영 + 정렬 SSOT 2:1 다이아몬드, elevationStep 0.25. SortingOrder = elevation·1000 + round((x'+y')·16). 시점 회전은 카메라가 아니라 viewQuarterTurns로.
DungeonHeight
Model		 elevation ↔ (floor, localHeight) elevation 4칸 = 던전 한 층. 음수 안전 내림 나눗셈이 핵심 (C# /는 0 방향 절삭이라 B2 이하가 어긋난다).

함정 — 여기서 실수가 가장 비싸다

  • WeakFloor/Hole/Empty는 SolidGround가 아니다 — 그래서 낙하가 이들을 관통한다.
  • DoorClosed/SecretDoor는 solid ground이지만 walkable이 아니고 시야도 막는다.
  • 용어를 섞지 말 것: 진행 지수(몇 번째로 방문하는 층 — 난이도 키) · FloorIndex(공간 구획) · Elevation(연속 높이) · LocalHeight(층 안 단차). TileKind.Floor는 또 다른 개념(걸을 수 있는 바닥 타입)이다.
  • 진행 순서 ≠ 고도 (v0.3.2 규약). 던전은 상승·하강·진입 깊이가 모두 가능하고 한 던전 안에서 올라갔다 떨어지는 경로도 가능하다. 그래서 진행 지수는 elevation의 함수가 될 수 없고 생성 시점에 층에 박히는 데이터여야 한다. 난이도는 얼마나 나아갔는가를 따르지 얼마나 높은가를 따르지 않는다.
  • 공간(위/아래) ≠ 진행(진출/귀환). StairsUp/Down은 공간 이름이라 고정이고, "다음 층으로 가는 계단"이 둘 중 무엇인지만 방향을 탄다. 같은 이유로 BottomFloorIndex(공간 최하단)와 FinalFloorIndex(진행 최종)는 다른 값이다 — 하강 던전에서만 우연히 같다.
  • 중력은 방향을 타지 않는다. FallRules·SightRules는 던전 방향을 모른다. 바뀌는 것은 규칙이 아니라 의미다 — 낙하는 하강에서 전진 지름길, 상승에서 후퇴·탈출 수단, 진입 깊이 던전에서는 진행과 무관한 지형 위험이다.

엄격 2단계다 — 에너지/속도 시스템이 없다. TurnNumber는 적 페이즈 완료 시 +1. 브레인은 Wait/Step/OpenDoor/Attack 의도만 돌려주고 위치·타일·연출 변경은 Gameplay가 한다 — 낙하·상태이상·연출이 이 틈에 끼어들 수 있는 이유다. 휴면(컬링) 중인 몬스터는 틱도 멈춘다(성능이자 규칙).

3.3 · 절차 생성 — 알고리즘은 임시, 불변식은 계약

현재 생성기는 축 정렬 3방 고정 템플릿 + seed 변형이다. BSP도 랜덤워크도 아니다. 이것은 버릴 임시 코드가 아니라 다층 던전의 생성 불변식을 먼저 못박기 위한 발판이며, 교체되는 것은 알고리즘뿐이다.

BSP로 갈아끼워도 통과해야 하는 계약

  • 문 밀봉 — 모두 열면 입구에서 전 walkable 도달, 닫으면 북쪽 방 차단
  • Hole은 정확히 한 층 아래 walkable에 착지(2층 관통 금지), 윗층 착지 컬럼은 다시 뚫지 않음
  • 층 간 기둥 겹침으로 착지 컬럼 보존
  • 적 스폰은 문 뒤에만 + 하행 계단 경비(1+depth)
  • 분기 방·비밀 방 보상 보장, 같은 seed = 같은 던전

전환의 실제 난도는 BSP 자체가 아니라 층-간 정렬이다. 각 층을 독립 BSP로 돌리면 "구멍이 아래층 진짜 바닥에 떨어진다"가 공짜로 나오지 않는데, 낙하·층간 시야·비밀방·AI가 전부 이 정렬에 의존한다. 선행 작업은 불변식 테스트를 생성기 구현과 분리해 계약 테스트로 만드는 것.

3.4 · 영속 — 세이브가 지형을 저장하지 않는 이유

RunSaveData — 판 안의 체크포인트

지형·적·아이템을 저장하지 않는다. seed로 재생성한다. 이어하기 = "현재 층을 층 입구에서 다시 시작". 계약은 dungeonId / stageCount / bossDefeated + 인벤 + 반입 장비 + 배고픔 + 사용한 휴식처 + 텔레메트리.

MetaSaveData — 판을 넘어가는 은행

골드·해금 영웅·창고·출정 로드아웃. ItemStack 목록 + ItemStorage 공용 연산으로 평탄화돼 있어 ItemKind에 값을 더하면 끝이다 (예전엔 종류마다 int 필드와 switch가 여섯 군데 있었다).

3.5 · 계측 — 밸런싱의 유일한 근거

RunTelemetry는 Unity 시간·파일을 모르는 순수 집계 모델이고, Gameplay가 이벤트와 unscaled delta를 먹인다. 사중 기록(런 총계 / 층별 / 구간별 / 소스별)이며, 구간(밴드) 롤업은 파생 값이라 따로 기록하지 않는다 — RefreshBands()가 저장·요약 직전에 다시 묶으므로, 경계를 바꾸면 과거 리포트도 같은 규칙으로 재분류된다. 치트 사용 런은 cheatsUsed로 표시해 정상 표본과 섞이지 않게 한다.

기둥 01

입체 공간 (Verticality)

기획 의도 — 공간 자체를 전술 자원으로 쓴다. 높이차는 여러 전술 축 중 하나이며 기둥 2와 대등하다 — 모든 전투의 답이 되어서는 안 된다. v0.3에서 어휘가 건물형으로 재정의됐다: 층이 수직의 주 단위이고, 층 사이는 계단실·붕괴 구멍·창문·엘리베이터 통로 같은 개구부로 잇는다. BG3식 연속 다높이는 지양하고, 층 내 높이차는 동기 있는 구조물에만 쓴다.

  • SafeFallHeight는 액터 스탯이며 장비(완충 부츠 +2)가 유일하게 올린다 — 뛰어내리기가 이동 수단이 되는 지점.

중력은 뒤집히지 않는다 — 그래서 낙하의 의미가 던전 방향을 탄다(v0.3.2). 하강 던전에서 낙하는 전진 지름길이지만, 첫 던전이 상승(폐병원)으로 확정되면서 진행 역행이 된다. 대신 후퇴·탈출 수단이 되어 익스트랙션·배고픔과 맞물린다 — 완충 부츠는 폐기되지 않고 전진 도구 → 탈출 도구로 의미만 바뀐다. FallRules는 한 줄도 바뀌지 않는다. 달라지는 것은 레벨 디자인상의 용도뿐이다 — 규칙과 용도를 분리해 둔 설계가 여기서 값을 한다.

높이를 실제로 쓰게 만드는 장치

층 안 무대 — 캐치워크

사다리 위 +2단 구조물을 밴드 길이만큼(Shallow 0 / Mid 1 / Deep·Boss 2) 얹는다. 결정론적 배치라 생성 RNG를 흔들지 않고, 사다리 링크로만 오르므로 도달성 불변식이 유지된다. 높이 인식 FOV 차폐·내려치기·고지대 사격이 실제로 발동하는 자리.

입체 전투 규칙

근접은 높이차 ≤ MeleeReachHeight(1)까지 닿고, 위에서 아래로 치면 DownStrikeBonus +1. 원거리는 RangedReachCost = 맨해튼 + |Δe|로 고지대에 사거리 예산을 과금한다 — 높이 이점이 공짜가 되지 않게.

남은 것 마법 시스템(높이를 처음부터 주인공으로: 아래로 흐르는 불 등)은 아직 없다. 도입 시 판정은 반드시 SightRules를 공유한다 — 지금 공유할 게 없어서 안 붙인 것뿐이다.

기둥 02

상호작용 & 상태이상

기획 의도 — 전투의 깊이는 여기서 나온다. 상태이상은 그 자체로 강한 것이 아니라 서로 반응해서 강해야 하고, 반응은 데이터 테이블로 남아야 새 조합이 코드 수정 없이 열린다.

두 층으로 나뉜 상태

액터 상태 — StatusEffects

Burn(턴당 고정 틱뎀) · Freeze(그 턴 행동 스킵) · Poison(독립 DoT).

  • 상쇄가 최우선 — Burn↔Freeze는 상호 소멸(CancelledOpposite, 둘 다 안 남음)
  • 아니면 max로 연장 — 재부여가 지속을 단축하지 않는다
  • Tick은 감소 전에 출력을 계산 — 마지막 틱도 반드시 발동한다
  • 결과 3종(Applied/Refreshed/CancelledOpposite)이 그대로 부여·연장·상쇄 팝업이 된다

타일 상태 — 별도 규칙

TileData.oiled / .wet에 얹힌 요소 반응. 액터 상태와 섞지 않는다.

  • OilRules — 3×3 Splash(젖은 타일은 기름을 거부), Ignite
  • WaterRules — ChainFreeze는 wet 타일 4연결 BFS라 반경 무제한, Evaporate는 3×3 국소
  • ShockRules — 물을 타고 전도되는 광역 감전
  • 물은 화상을 끈다 — 몬스터가 이걸 알고 있다(아래)

몬스터 AI — 행동 트리로 이관됨

손으로 쓴 FSM에서 Behavior Tree로 옮겼다(2026-07-25). 콘텐츠가 늘어도 분기 가독성을 유지하려는 것이고, 경량 프리미티브(Selector/Condition/Leaf)만 쓴다. 공개 API와 동작은 이관 전후 완전히 동일하며 테스트가 오라클 역할을 했다.

기둥 03

제한된 시야 (Limited Sight)

기획 의도 — 모든 걸 보여주지 않는다. 정보의 부재가 곧 긴장이다. 그래서 이 기둥은 렌더링 기능이 아니라 정보 접근 정책이며, HUD와 연출까지 여기에 종속된다.

판정은 SightRules 하나가 소유한다

원래 시야/사격 판정은 세 곳(GridVisibility FOV · CombatRules.HasLineOfSight · VerticalOpeningRules)에 흩어져 있었고 같은 높이만 알았다. 3단계에 걸쳐 하나로 합쳤다 — "높이가 달라도 실제로 보이면 보고 쏜다"가 성립한다.

함수담당규칙
HasLineOfSight수평·경사2D 브레젠험 + 시선 elevation 보간(복셀 차폐). 같은 컬럼이면 수직으로 위임.
HasVerticalSight같은 컬럼허공은 통로, 온전한 바닥은 차단 — 즉 실제 Hole만 층을 잇는다.
ViewColumnFOV 컬럼 해석컬럼을 높이맵이 아니라 span으로 — 눈높이 이하 지면 + 눈높이 위 머리 위 구조물.
ViewFromFloor층간 미리보기오직 Hole만 포털. StairsUp/Down은 아니다.
CanReachAcross근접 도달 기하평면 인접 + 높이차. CombatRules.AreAdjacent가 위임한다.

절대 깨면 안 되는 뿌리

  • void(타일 없는 컬럼) = 불투명. 이 던전은 방 경계를 벽 타일이 아니라 타일 부재로 표현하므로(벽은 비주얼 전용), 이 규칙이 "닫힌 문 뒤 방 = Unknown" 불변식의 핵심이다. 단, 수평 규칙이라 수직에는 적용하지 않는다 — 수직에서 허공은 통로다.
  • 렌더 ≠ 시뮬. 시야가 높이를 알아도 화면은 여전히 활성 층 + Hole 국소 미리보기만 노출한다.
  • 컬럼당 여러 솔리드 구간을 인식해야 한다 — B2 위에 B1 바닥이 얹히므로 단순 높이맵이 아니다.
  • HeightBlockThreshold(1) — 1단 단차는 안 막고 2단 이상만 벽처럼 막는다.

정보 차단은 렌더링이 아니라 규칙이다

EnemyPresentationRules.ShouldShowFeedback을 통과하지 못한 적의 피해 숫자·플래시·사망 문구· 상태 FX는 생성 자체가 되지 않는다. 폭발 적중 수도 보이는 대상만 센다. 전투 결과와 처치 전적은 정상적으로 반영되지만 HUD로 누설하지 않는다 — "화면에 안 보이는 적의 상태를 이펙트로 추측"할 수 있으면 기둥 3이 무너지기 때문이다. 시체는 3턴간 페이드 후 월드·탭 대상·전투 목록에서 함께 제거된다.

FloorVisibilityRules는 순수 boolean 정책이다 — debugAll → 전부 / 활성 층 → visible‖explored / 그 외 → verticalPreview일 때만. 다른 층의 Explored 기록은 미니맵·세이브에는 남기되 월드 지오메트리에는 그리지 않는다.

기둥 04

파밍 & 조합

기획 의도 — 자원을 모으고 조합해 메타로 잇는다. 이 기둥이 하드 타이머를 금지한다: 제한 턴은 탐색·조합·숨은 방을 통째로 죽이므로, 압박은 자원으로 관리되는 것이어야 한다.

공간이 곧 자원 — 6×4 멀티슬롯

백팩은 개수가 아니라 면적이다. Relic 2×2, 기름병/투척단검/귀환두루마리 1×2, 나머지 1×1. 회전 없음. BackpackRules.TryCreateLayout은 결정적·큰 것 우선·행 우선 그리디이며 정렬 키가 면적↓ → 높이↓ → KindOrder↑ → InstanceIndex↑라 같은 아이템 집합은 항상 같은 배치가 된다.

  • all-or-nothing — 하나라도 못 놓으면 전체 실패(null). 면적이 남아도 조각화로 실패할 수 있고, 그게 설계된 동작이다.
  • 공간이 없으면 월드 아이템은 바닥에 남는다 — 조용히 사라지지 않는다.
  • 허브 창고는 대량 보관용이라 종류별 중첩이다. 던전 백팩의 면적 규칙과 의도적으로 다르다.
  • 장착 장비는 백팩 공간을 쓰지 않고 출정 격자에도 안 나온다(대장간이 관리).

익스트랙션 — 이 게임의 판돈

배고픔 — 부드러운 시계

포만 → 배고픔(경고만, HP 불변) → 굶주림(주기적 HP 1). 즉사시키지 않고 신호만 준다. 가득 찬 배 100턴 / 통조림 한 통 60이라 한 층(40~60턴)을 겨우 버티는 짧은 주기이고, 판 전체를 관통하며 모닥불로는 배가 차지 않는다. 결과적으로 "다음 탈출구까지 버틸 식량이 있나"가 곧 더 내려갈지의 답이 된다 — 익스트랙션과 짝을 이루는 구조.

장비 — 숫자가 아니라 규칙

어떤 장비에도 공격력 보정이 없다. GDD §11이 경계한 것은 영구 스탯 강화였고, 권한 것은 장비/시작 장비 해금이다. 옛 대장간 영구 티어 강화는 제거됐다.

§8 · 횡단

기둥을 서로 밀어붙이는 압력

기둥은 각자 잘 서 있는 것으로 충분하지 않다. 아래는 기둥끼리 충돌하게 만드는 장치들이며, 창발적 전술은 여기서 나온다.

원거리 몬스터 (투석 약탈자)

적 4종이 전부 근접이면 플레이어만 원거리를 갖고 위치 선택이 위협받지 않는다. 사수가 붙기 전에 쏘기 시작하면서 엄폐·높이·돌진이 처음으로 의미를 갖는다. 기둥 1 ↔ 기둥 3의 충돌면.

하행 계단 경비병

북쪽 방 스폰만으로는 완주 동선(남쪽 방→하행 계단)이 전투를 완전히 우회한다(시뮬로 발견). 하행 계단 인접에 1+depth를 추가 배치 — 깊을수록 무거운 관문.

숨은 방

B1~B9 중 seed로 고른 3개 층. 공개 전에는 벽처럼 이동·FOV를 막고(기둥 3), 인접 조사 또는 3×3 폭발로 공개된다(기둥 2). 보상은 결정적 — B4+ Relic, 그 외 Gemstone(기둥 4).

깊이 밴드 변주

DungeonBandProfile 하나가 구간 정체성의 SSOT다. 변주의 통로는 세 가지뿐 — 밴드 스프라이트 슬롯 · 구조(캐치워크 길이) · 광원 밀도. 팔레트는 깊이로 바뀌지 않는다(테스트로 고정).

프레젠테이션 계층 — Core의 의도를 세계로

IsoPrototypeDemo가 던전과 허브를 실제로 세우고 굴리는 중심 MonoBehaviour다. 현재 partial 19개 · 약 8,500 LOC이며, 이벤트 (PlayerHpChanged·ActiveFloorChanged·ExitChoiceRequested…)로 HUD와 느슨하게 결합한다. CombatPresentationRules가 source를 물리/화염/냉기/강타로 분류해 FX 수치만 넘기고, 실제 돌진·스쿼시·버스트·카메라 흔들림은 Gameplay가 만든다 — Core에는 연출 코드가 없다.

확정된 프레젠테이션 방침: 캐릭터 애니메이션은 Aseprite 클립 파이프라인 (절차적 트윈은 상태 FX 정도만), UI 인터랙션은 DOTween — 단 화면 UI는 UI Toolkit이라 DOTween이 직접 붙지 않는다. VisualElement에는 experimental.animation/USS transition을 쓴다.

§10 · 리스크 & 다음

지금 아키텍처의 부채

등급항목내용과 방향
높음 IsoPrototypeDemo 신(神) 클래스 partial 19개 · 약 8,500 LOC. 더 쪼개는 것으로는 해결되지 않고 실제 분리 (월드 빌드 / 턴 실행 / 연출)가 필요하다. 씬 와이어링 리스크가 커서 테스트를 돌릴 수 있을 때 손대는 것이 맞다.
높음 생성기 BSP 전환 3방 고정 템플릿을 룸-앤-코리더/BSP로 교체. 난도는 알고리즘이 아니라 층-간 정렬 보장이다. 선행: 불변식 테스트를 생성기 구현과 분리(계약 테스트화).
중간 문서 드리프트 ARCHITECTURE.md의 규모·테스트 수치(Core 41파일/4,785 LOC, 646 케이스)와 ROADMAP.md의 환경 현황(Unity 6000.5.0f1, asmdef 3개)이 실제와 어긋난다. GDD 본문도 "모바일 전용" 시점이다. 실측은 아래 각주.
해결 진행 지수가 고도에서 파생됨 DepthIndex = Math.Max(0, −floorIndex) 파생을 제거했다. DungeonFloorInfo.ProgressIndex를 1급 필드로 두고 생성기가 부여하며, DungeonDepthBandRules.ForFloor는 삭제, 파생식 8곳은 레이아웃 조회로 교체했다. 부수로 BottomFloorIndex가 진행 최종과 공간 최하단 두 뜻으로 섞여 쓰이던 것도 FinalFloorIndex로 갈라냈다. 단, Unity 미검증 — 로컬 회귀 실행이 남아 있다.
중간 생성기가 방향을 읽지 않음 방향은 던전별 데이터로 선언됐으나(폐병원=상승, 침수된 금고=진입 깊이) 생성기는 아직 하강만 만든다. 좌표계는 거의 그대로지만(FloorIndex는 양수도 이미 정상, FallRules는 중력 절대) 층 루프 방향·링크 방향·Hole 생성 순서가 뒤집힌다. 표시 리스킨만 먼저 나가면 라벨과 실제 구조가 어긋나므로 묶어서 처리한다.
중간 지역 정체성 부재 DungeonCatalog에 침수된 금고·잿불 성채가 예고돼 있으나 seed·floorCount만 다르고 로스터·밴드·보상이 전 지역 공용이다. 지금 열면 같은 던전을 seed만 바꿔 도는 것 — 선행 조건은 "다른 적".
낮음 크로스-층 몬스터 활성화 "보이는 Hole 인접 아래층 몬스터"는 MonsterActivation에 TODO로 남아 있다(설계상 예정된 자리).
낮음 규칙 클래스 ↔ 파일명 불일치 CombatRules가 CombatantState.cs에 있는 등. 탐색성만 보면 분리가 낫지만 현재 응집도도 합리적이고 asmdef/테스트 영향이 없다 — 낮은 우선순위.
검증 Unity 화면 확인 잔여 캐치워크 격자 룩, 등잔 밀도, B10 제단 실루엣과 전조 노출 타이밍은 코드는 됐지만 Game View 확인이 남아 있다.

다음 한 걸음 (권장 순서)

  1. Unity 회귀 실행. 진행 지수 분리·방향 데이터 모델이 모두 Unity 없는 환경에서 작성돼 컴파일·테스트가 미검증이다. 다른 무엇보다 먼저다.
  2. 생성기가 방향을 읽게 한다. 하강이 박힌 곳은 세 군데뿐이며 (FloorIndex = -depth · 진출 계단을 Down으로 고정한 링크 · 낙하 바닥), 규칙과 계약 테스트는 이미 있다.
  3. 계측 공백. 내려치기 발동 · 높이차 사격 · 창문 파괴 · 탈출구에서 「계속 탐색」 — 기둥 1의 v0.3 콘텐츠가 실제로 쓰였는지 지금 리포트로는 알 수 없다. 장비는 RunSaveData.carriedWeaponId/GearId가 이미 있으므로 런 종료 시 스냅샷이면 된다.
  4. 실플레이 리포트. B1~B10 텔레메트리로 밀도·피해 급증 구간·아이템 활용도를 확인한다 — 아래 밸런싱 판단이 전부 여기에 의존한다. 소요 시간은 판정이 아니라 밀도 지표로 읽는다.
  5. 플레이어 원거리 재조정. 적 압박(사수)이 생겼으니 M5의 너프(피해 1·사거리 4)를 다시 본다.
  6. 불변식 계약 테스트 분리. BSP 전환의 안전망을 먼저 깐다.
  7. 밴드 프로파일을 (지역, 깊이)로. 두 번째 원정지를 여는 유일한 선행 조건.
  8. 문서 정합. ARCHITECTURE.md/ROADMAP.md 수치와 GDD의 플랫폼 시점을 현재 상태에 맞춘다.
