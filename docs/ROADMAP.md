# 로드맵 & 진행 상태

> 원칙: **각 마일스톤은 "플레이 가능한" 상태로 끝난다.** 앞 단계 없이 뒷 단계로 점프 금지. **M1 완주 최우선.**
> 전체 기획·상세 근거는 `GDD.md` §8. 이 파일은 작업 추적용 요약.

## 현재 개발 우선순위 (임시)

- **모바일 보류 · PC 우선.** 모바일 세로·다해상도 검증과 이원 View 유지가 개발을 느리게 해서,
  당분간 PC(데스크톱)만 개발·검증 타깃으로 둔다. 상세 규칙은 `CLAUDE.md`의 "현재 개발 우선순위".
- 입력 추상화·`ResponsiveUiLayout`·이원 UXML 코드는 **삭제하지 않고 유지**한다(재개 시 재작업 방지).
  PC 에디터/빌드는 `HudPresentation.Auto`가 이미 `Desktop`으로 해석되므로 별도 코드 변경은 없다.

## 전투 깊이 — 적 다양성 (진행 중)

> 시스템 축(상태이상·원소 반응·낙하·높이)은 두꺼운데 **적이 얇았다**. 4종 전부 근접이라
> 플레이어만 원거리를 갖고, 위치 선택이 위협받지 않았다(M5는 이 카이팅을 적의 압박이 아니라
> *플레이어 원거리 너프*로 눌러놨다). 높이 시스템도 적이 쓰지 않으면 장식이다.

- [x] **원거리 적 1종 — 투석 약탈자(Slinger)** — `MonsterArchetype`에 사거리/원거리 피해/
  거리 유지값을 추가하고, 행동 트리에 `DecideRanged`(거리 벌리기 → 사격 → 사선 잡기)를 붙였다.
  판정은 플레이어와 같은 `CombatRules`/`SightRules`를 쓰므로 높이차가 사거리 예산에 그대로 물린다.
  Mid 밴드부터 등장(Shallow 0). **수치는 실플레이 전 임시** — HP4/근접1/원거리2/사거리4/유지2.
- [x] **장비 시스템 — 숫자가 아니라 규칙을 바꾸는 4종** — 긴 파이프(근접 사거리 2·직선),
  대형 렌치(명중 시 1칸 넉백 → 구멍·창문으로 유도), 표지판 방패(받는 물리 피해 -1, 백팩 2×2),
  완충 부츠(안전 낙하 높이 +2). **공격력 보정은 어느 장비에도 없다** — GDD §11이 경계한 것은
  영구 스탯 강화였고 권한 것은 장비 해금이다. 대장간의 영구 티어 강화(무기 연마/방어구/도구)를
  **제거하고** 장비 제작·장착으로 대체했다. 장착 장비는 백팩 공간을 쓰지 않는다.
- [x] **장비도 익스트랙션 규칙(다크앤다커 모델)** — 장착 장비는 출발 시 창고에서 빠져 원정에
  반입되고 죽거나 포기하면 소모품과 함께 잃는다. 살아 나오면 창고로 돌아오고 장착도 유지된다.
  창고에 남긴 예비 장비는 안전하다. 반입 기록은 체크포인트에 저장돼 이어하기·던전 체인에서
  이어지며, 던전 체인 전환이 창고를 두 번 털지 않도록 반입은 새 원정 출발에서만 일어난다.
- [x] **던전 장비 드랍** — B4부터 층당 최대 하나(30%). 주우면 백팩 면적을 먹고 빈 슬롯이면
  즉시 장착되며, 그 순간부터 죽으면 잃는다. "주워서 살아 나와야 내 것"이 성립한다.
- [x] **배고픔** — SPD 계보의 부드러운 시계. 포만 → 배고픔(경고만) → 굶주림(주기적 HP 감소).
  통조림이 답이며 던전·상점 양쪽에 있다. 하드 타이머 대신 이걸 쓴 이유는 파밍(기둥 4)을
  죽이지 않으면서 무한 캠핑·왕복만 막기 위해서다. 배고픔은 판 전체를 관통한다(모닥불도 배는 못 채운다).
  주기는 짧게 잡았다 — 가득 찬 배 100턴/한 통 60이라 한 층을 겨우 버티고 중간중간 자주 먹는다.
  **배고픔 단계에 붙일 별도 상태이상은 후속**(HP는 건드리지 않는다).
- [x] **중간 생환** — 비상 탈출구는 **B4·B8 두 곳뿐**이고, 밟으면 "계속 탐색 vs 생환"을 묻는다.

  "다음 탈출구까지 버틸 식량이 있나"가 곧 진행 판단이 된다.

## 향후 기술 과제 — 던전 생성기 BSP/룸-앤-코리더 전환

> 현재 생성기(§M1)는 **3방 고정 템플릿 + seed 변형**이다. 이는 다층 던전의 **생성 불변식을 먼저
> 못박기 위한 발판**이며, 최종 목표는 `GDD.md` §5.8의 **진짜 룸-앤-코리더/BSP 생성기**다
> (근거: `DungeonLayout.cs:82` 주석, `SYSTEMS.md`의 "이후 확장(진짜 룸-앤-코리더/BSP)에서도 이 연결
> 그래프와 생성 불변식을 유지한다" 문장). 교체 대상은 생성 알고리즘뿐 — 불변식은 계약으로 유지한다.

- [ ] **생성기 내부를 BSP/룸-앤-코리더로 교체** — 방 배치·복도 카빙을 알고리즘으로 다양화한다.
- [ ] **불변식 계약 테스트를 생성기 구현과 분리**(제너레이터 무관) — BSP로 갈아끼워도 그대로 통과해야 한다:
  문 밀봉(열면 도달·닫으면 북쪽 방 차단) · Hole은 정확히 한 층 아래 walkable 착지(2층 관통 금지) ·
  층 간 기둥 겹침으로 착지 컬럼 보존 · 적은 문 뒤에만 · 하행 계단 경비 · 분기/비밀 방 보상.
- [ ] **층-간 정렬 설계** — 각 층을 독립 BSP로 돌리면 "구멍이 아래층 진짜 바닥에 착지"가 공짜로 안 나온다.
  낙하·층간 시야·비밀방·AI가 이 정렬에 의존하므로, BSP 분할 위에서 정렬을 보장하는 방식이 전환의 핵심 난도.
- 상세 설계 배경: `docs/ARCHITECTURE.md` §7.4.

## 향후 기술 과제 — 3D 시야선(높이 인식) · 입체 전투

> 시야/사격 판정은 원래 같은 높이만 알았고 세 곳(`GridVisibility` FOV · `CombatRules.HasLineOfSight` ·
> `VerticalOpeningRules`)에 흩어져 있었다. **세 축 모두 `SightRules` 하나로 합쳐졌다** —
> 전투 LoS는 높이 보간(1단계), 개구부·근접은 흡수·공유(2단계), FOV 셰도우캐스팅의 컬럼 해석은
> `ViewColumn` 위임(3단계). "높이가 달라도 실제로 보이면 보고 쏜다"가 성립한다.
> 남은 것은 이 토대 위에 얹을 **입체 전투 콘텐츠**(아래 "관련 향후 과제")다.

지켜야 할 뿌리(불변):
- **void = 불투명** ("닫힌 문 뒤 방 = Unknown") — void 컬럼은 무한 높이 벽으로 취급해 유지.
- **렌더 ≠ 시뮬** — 시야가 높이를 알아도 화면은 여전히 활성 층 + Hole만 노출.
- **컬럼당 여러 솔리드 구간(천장/공중)** 인식 — B2 위에 B1 바닥이 얹히므로 단순 높이맵이 아니라 span-aware 판정.

단계 (작은 것 → 큰 것, 눈에 보이는 순서 — 뒤 단계가 앞 단계 함수를 재사용):
- [x] **1단계 — 전투 LoS 높이 인식**: `HasLineOfSight`를 높이 보간(복셀 차폐) 판정으로 교체 —
  평면(from.e==to.e)은 기존과 완전히 동일, void=불투명 유지, 같은 컬럼 수직 투시는 2단계로 보류.
  높이차 사격 개방 + `RangedReachCost`(맨해튼+|Δe|)로 고지대에 사거리 비용 부과(카이팅 억제).
  Core 테스트 `LineOfSight3DTests` + `FiringPositionTests` 갱신.
- [x] **2단계 — 판정 통합**: 시야·도달 판정을 `SightRules` 하나로 모았다.
  `VerticalOpeningRules`는 **흡수·삭제**(`ViewFromFloor`/`VerticalOpeningView`가 `SightRules`로 이사)했고,
  같은 컬럼 수직 시야(`HasVerticalSight`)가 열렸다 — 허공은 통로, 온전한 바닥은 차단
  (`TileData.BlocksVerticalSight`)이라 실제 개구부만 층을 잇는다. 개구부 투시도 이 함수를 거치므로
  사이에 낀 바닥이 시야를 막는다. 근접은 `SightRules.CanReachAcross`로 도달 기하를 공유한다
  (`CombatRules.AreAdjacent`는 위임). **마법은 아직 시스템이 없어 공유할 판정이 없다** — 도입 시 같은 함수를 쓴다.
  Core 테스트 `SightRulesTests`(옛 `VerticalOpeningRulesTests` 흡수).
- [x] **3단계 — FOV/안개까지 높이 반영**: 셰도우캐스팅의 컬럼 해석을 `SightRules.ViewColumn`으로
  옮겨 시야 판정을 전투 LoS와 한 출처로 합쳤다. 컬럼을 높이맵이 아니라 **span**으로 본다 —
  눈높이 이하의 **지면**과 눈높이 위의 **머리 위 구조물**을 각각 결과에 넣으므로,
  캐치워크 아래 바닥도 실제로 보이고(예전엔 맨 위 표면 하나만 보여 안개로 남았다)
  캐치워크 위에 서면 눈높이가 올라가 아래가 이어져 보인다. 차단 규칙(void=불투명 ·
  머리 위 구조물 · 벽/닫힌 문)과 `HeightBlockThreshold`(1단은 안 막음)는 그대로 유지했다.
  단일 elevation 대역(테스트·대부분의 평면 층)에서는 결과가 이전과 완전히 동일하다.
  Core 테스트 `ShadowcastFovTests`(캐치워크 span 2건) + `SightRulesTests`(ViewColumn 5건).
- 상세 개념: `docs/ARCHITECTURE.md` §5(시야).

관련 향후 과제(방향만, 미확정):
- [x] 낙하 데미지 **높이 기반화** (층 안 발판 낙하도 데미지) — **구현 완료**: `FallRules.DamageForDrop`
  (`eff=max(0,dropCells−SafeFallHeight)`, `round((eff/EPF)(eff/EPF+1))`, EPF로 나눠 2/6/12 재현), `TryFall`이
  실제 칸수로 계산, `SafeFallHeight` 파라미터 자리 확보. `FallRulesTests` 곡선·EPF·층 안 낙하 케이스. 이하 원안:
- 낙하 데미지 **높이 기반화** (층 안 발판 낙하도 데미지) — **확정 곡선(가속)**: 지금 층 기반 값
  (1층 **2**·2층 **6**·3층 **12**)을 그대로 유지하되 층 안 낙하도 작게 데미지. `eff = max(0, 낙차칸 − SafeFallHeight)`,
  `데미지 = round(eff/4 × (eff/4 + 1))`, 기본 SafeFallHeight `0`(곡선이 1칸을 무료로 만듦) → 1칸 0·2칸 1·1층 2·2층 6·3층 12.
  SafeFallHeight는 액터 스탯(장비로 상향). 구현: `FallRules`(Core) 곡선 교체 + `FallRulesTests` 갱신 — 높이 시스템의 **첫 작은 조각**.
- **입체 전투**: 근접 단차 타격·내려치기 보너스, 고지대 원거리, 근접 넉백으로 발판 아래 낙하 유발.
- **마법 시스템**(현재 없음): 높이를 처음부터 주인공으로(아래로 흐르는 불 등).
- **장비 시스템**(현재 없음): `SafeFallHeight`/`ClimbHeight` 같은 액터 스탯의 출처.
